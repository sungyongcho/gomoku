# Measuring Strength When the First Player Wins

In this Gomoku variant (19×19 with captures to 5 pairs and double-three forbidden), Black holds a large first-move advantage between equal players. Once the v5 training run (`6x96`) strengthened, that first-player skew dominated both the 40-game promotion gate described in [Model Evaluation: Arena and SPRT](/docs/alphazero/evaluation) and the round-robin ladders. Evaluating models accurately required balancing colour pairs, replacing 4-ply random openings with 3-ply openings, increasing game counts to match confidence-interval widths, tracking strength against fixed outside models at equal thinking time, ranking checkpoints in a Bradley–Terry round-robin ladder, and inspecting replay diagnostics beyond win rate.

## First-Player Advantage and Opening Plies

### Why 4-Ply Openings Made the Gate Colour-Determined

During self-play in iterations 131–135 (1,200 games per iteration, 800 searches per move), the side that moved first after the random opening won most games regardless of strength ([`v5-small-6x96-cont8.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont8.yaml#L5-L10)):

| Random opening plies | Side moving first in search | Measured Black win rate | Distance from 50% |
| ---: | --- | ---: | ---: |
| 0 | Black | 87% | 37 pts |
| 1 | White | 66% | 16 pts |
| 2 | Black | 79% | 29 pts |
| 3 | White | 38% | 12 pts |
| 4 | Black | 82% | 32 pts |

Even-ply random openings (0, 2, 4) leave Black to place the first searched stone, pushing Black's win rate to 79%–87%. Odd-ply openings (1, 3) hand the first searched move to White after an odd number of random stones: at 1 ply Black still won 66% with the extra random stone, whereas at 3 plies White's first searched move lowered Black's win rate to 38% (12 percentage points from 50%, the closest to even of the five settings).

Through `v5-small-6x96-cont7.yaml`, both the promotion gate (`eval_random_opening_plies: 4`) and the ladder (`opening_plies: 4`) used 4-ply random openings, where Black won 82% of self-play games. At iteration 135, every pairing in the ladder scored 9–11 out of 20, and the promotion gate finished 40–40: almost every pair of games simply split 1–1 with Black winning both sides, masking genuine playing-strength differences. Commit [`e82d5c5`](https://github.com/sungyongcho/gomoku/commit/e82d5c5) kept 4-ply openings in `cont7`, and `v5-small-6x96-cont8.yaml` switched both the promotion gate and the ladder to 3-ply openings (`eval_random_opening_plies: 3`, `opening_plies: 3`), which `cont9`, `v6`, and `v6b` kept.

### Colour-Balanced Evaluation Pairs

When one colour wins 82% of games, giving a challenger even two extra games as Black shifts its expected score in a 40-game match from 50.0% to `(22 × 0.82 + 18 × 0.18) / 40 = 53.2%`, consuming more than half the margin to the 55% promotion threshold. Before commit [`147dee5`](https://github.com/sungyongcho/gomoku/commit/147dee5), [`RayEvalRunner.run_evaluation`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/runners/ray_eval_runner.py#L151-L169) split `num_games` across workers with `num_games // num_workers`, which could assign an odd game count to a worker and leave colours unpaired.

Commit [`147dee5`](https://github.com/sungyongcho/gomoku/commit/147dee5) changed the worker distribution to assign **whole pairs per worker** so that each worker plays every seeded opening once as Black and once as White:

```python
# alphazero/gomoku/alphazero/runners/ray_eval_runner.py:151-168
# Whole pairs per worker: each pair plays one opening once with each colour.
pairs, odd_game = divmod(num_games, 2)
base, remainder = divmod(pairs, self.num_workers)
futures = []

for idx, w in enumerate(workers):
    count = 2 * (base + (1 if idx < remainder else 0))
    count += 1 if idx == 0 and odd_game else 0
    if count > 0:
        futures.append(
            w.run_duel.remote(
                games=count,
                eval_cfg=eval_cfg,
                opening_turns=eval_cfg.eval_opening_turns,
                temperature=eval_cfg.eval_temperature,
                blunder_threshold=eval_cfg.blunder_threshold,
                opening_seed=idx * 100_000,
            )
        )
```

Inside [`_run_duel`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/arena.py#L133-L191) and [`_random_opening`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/match.py#L44-L56) (added in [`9f09c80`](https://github.com/sungyongcho/gomoku/commit/9f09c80)), each pair index `pair = i // 2` seeds `np.random.default_rng(opening_seed + pair)`, places `random_opening_plies` legal stones (stopping early if a random stone terminates the game), and alternates which engine moves first (`i % 2 == 0`).

## Score, Confidence Intervals, and Sample Size

For $N$ head-to-head games with $W$ wins, $D$ draws, and $L = N - W - D$ losses, every evaluation path in the repository (`reference_match.py`, `metrics.py`, `run_ray.py`, and `eval_local.py`) scores each game as $x_i \in \{1,\, 0.5,\, 0\}$ and defines the match score as:

$$
s = \frac{W + D/2}{N}
$$

### Standard Error and Confidence Interval

In [`eval_local.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/eval_local.py#L220-L225), the 95% confidence interval is computed directly from the empirical standard deviation of the per-game scores $x_i$:

```python
# alphazero/gomoku/scripts/eval_local.py:220-226
score = sum(r.a_score for r in results) / len(results)
margin = 1.96 * float(np.std([r.a_score for r in results])) / math.sqrt(len(results))
print(
    f"{a.name} vs {b.name}: +{wins} ={draws} -{losses} of {len(results)} "
    f"score={score:.3f} 95%=[{max(0, score - margin):.3f},{min(1, score + margin):.3f}] "
    f"elo={elo_difference(score):+.0f}"
)
```

Expanding $\sigma^2 = \frac{1}{N}\sum_{i=1}^{N} (x_i - s)^2$ in terms of the win rate $w = W/N$ and draw rate $d = D/N$ gives:

$$
\text{SE} = \frac{\sigma}{\sqrt{N}} = \sqrt{\frac{s(1 - s) - d / 4}{N}}, \qquad \text{CI}_{95\%} = \bigl[\max(0,\; s - 1.96\,\text{SE}),\;\; \min(1,\; s + 1.96\,\text{SE})\bigr]
$$

When draws are absent ($d = 0$), $\sigma = \sqrt{s(1 - s)}$ reduces to the binomial standard deviation, which is at most $0.5$ when $s = 0.5$.

### Implied Elo Difference

[`elo_difference`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/eval_local.py#L187-L189) maps the score $s$ (clamped to $[10^{-3},\; 1 - 10^{-3}]$) to an Elo difference:

$$
\Delta = -400 \log_{10}\!\left(\frac{1}{s} - 1\right) = 400 \log_{10}\!\left(\frac{s}{1 - s}\right)
$$

```python
# alphazero/gomoku/scripts/eval_local.py:187-189
def elo_difference(score: float) -> float:
    clipped = min(max(score, 1e-3), 1 - 1e-3)
    return -400 * math.log10(1 / clipped - 1)
```

For reference, `s = 0.550` corresponds to +35 Elo, `s = 0.540` to +28 Elo, and `s = 0.750` to +191 Elo (while [`calculate_elo_from_win_rate`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/metrics.py#L6-L37) uses the same formula clamped to `[0.01, 0.99]`).

### How Many Games a Difference Needs

For a 95% confidence interval half-width $1.96\,\text{SE}$ to stay at or below a target margin $\delta = |s - 0.5|$, the required game count is approximately:

$$
N \ge \left(\frac{1.96\,\sigma}{\delta}\right)^2 \approx \frac{0.96}{\delta^2} \quad (\text{around } s \approx 0.5,\; d = 0)
$$

That scaling governs what each match size in the repository can resolve:

- **40 games (`v5-small-6x96.yaml`)**: Near $s = 0.50$, the 95% margin is $\pm 0.155$ (`±113` Elo). Under a fair binomial coin flip ($s = 0.50$), equal models reach $\ge 22 / 40$ (55%) **32% of the time** (31.8% exact, as noted in [`v5-small-6x96-cont4.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont4.yaml#L15)).
- **80 games (`v5-small-6x96-cont4.yaml` onward)**: Halves the variance, narrowing the 95% margin at $s = 0.50$ to $\pm 0.110$. Between iterations 64 and 100, the latest model scored 49.6% over 480 promotion games (`cont4.yaml`), while a +35 Elo edge ($s = 0.55$, $\delta = 0.05$) still requires roughly 380 games for its 95% confidence interval to clear 0.50.
- **300 games (`v6b-10x128-cont1.yaml`, `cont2`)**: Narrows the 95% margin at $s = 0.50$ to $\pm 0.057$. In `cont2`, scores of 0.460, 0.480, and 0.497 over 300-game matches are noted as still lying within single-match noise even though the series rose monotonically.

Early stopping via the Sequential Probability Ratio Test (`use_sprt`) remained available in [`arena.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/arena.py#L193-L204) and is documented in [Model Evaluation: Arena and SPRT](/docs/alphazero/evaluation), but all v5 and v6 runs kept `use_sprt: false` for fixed-length comparisons.

## Reference Matches: Equal Searches vs. Equal Thinking Time

The promotion gate only compares a checkpoint with its immediate champion (`champion_path`), so it cannot tell whether a new run has caught up to a differently sized model, and when the gate stops promoting it tests every candidate against a frozen checkpoint.

### Fixed Reference Matches (`e89ced7`)

Commit [`e89ced7`](https://github.com/sungyongcho/gomoku/commit/e89ced7) added [`reference_match.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/reference_match.py#L50-L185) and wired it into [`run_ray.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/pipelines/run_ray.py#L941-L977). Every `every_iters` iterations, the runner plays `num_games // 2` seeded opening pairs (`opening_plies: 2` initially, 3 in v6/v6b) with colours swapped and deterministic search ([`match_mcts`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/reference_match.py#L50-L60): `time_limit_s: None`, `batch_infer_size: 1`, `dirichlet_epsilon: 0.0`, `exploration_turns: 0`).

Against the `12x128` V4 champion (iteration 222) at 400 searches each (40 games per match unless noted), v5 (`6x96`) progressed as follows across its continuation configs (see [A Smaller Network Trained Properly](/docs/optimization/training-v5) for the training changes):

- **Iterations 24 and 28**: Lost 4–36 (0.100) and 6–34 (0.150), prompting the self-play jump from 400 to 800 searches in [`v5-small-6x96-cont.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont.yaml#L5-L13).
- **Iteration 50**: Lost 27 of 40 games (0.325), median 10 plies, from random openings because v5 had only played near one star point (`cont2`).
- **Iteration 56**: Lost 40 of 40 games from a centre opening and scored `19/40` from random openings; fine-tuning for one epoch with translation augmentation raised the local 40-game score at 400 searches to `26/40` on random openings and `34/40` from the centre (`cont3`).
- **Iterations 64–100 to `cont6`**: Scored 0.725–0.875 on the cluster and 0.75–0.80 locally (`cont4`), rose to 0.95 under `cont4` (`cont5`), and reached 39–1 (0.975) at equal searches by `cont6`.

Because running 40 reference games in the cluster took 58 minutes compared to 12 minutes locally (`v5-small-6x96-cont5.yaml`), `cont5` removed the automatic in-cluster V4 reference match and moved V4 checks offline.

### Equal Thinking Time (`719fe38`)

Once a match compares two networks of different size (`10x128` v6/v6b against `6x96` v5 iteration 144), equal search counts test the wrong constraint. On a C4D worker (`bfloat16`, batch 8), `10x128` (`3.33M` weights) took 39 ms per batch against 16 ms for `6x96` (`1.36M` weights), roughly 2.5x slower (`v6-10x128.yaml`). On two Neoverse-N1 cores of the Oracle A1 serving host (`static int8 ONNX`, 2 threads, 2.5 s budget), [`bench_search`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L14-L19) measured 272 searches for `10x128` versus 634 searches for `6x96` (see [Answering by the Clock](/docs/optimization/time-limited-serving)).

Commit [`719fe38`](https://github.com/sungyongcho/gomoku/commit/719fe38) added two fields to [`ReferenceMatchConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L197-L215):

1. `reference_searches: int | None = None`: gives the reference model its own search budget in [`run_reference_match`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/reference_match.py#L157-L163) so each network gets the number of simulations it completes in equal wall-clock time (640 vs 1600 in `v6-10x128.yaml` for the 2.5x C4D ratio, then 270 vs 630 in `v6b-10x128*.yaml` from iteration 14 onward to match the Oracle A1 2.5 s budgets).
2. `player: Literal["champion", "latest"] = "champion"`: lets [`run_ray.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/pipelines/run_ray.py#L948-L955) test the `latest` checkpoint even when the promotion gate has stalled.

That distinction decided deployment: at equal search counts (1,600 each, 200 games in `v6b-10x128.yaml`), v6b iteration 12 beat v5 iteration 144 (0.540), whereas at equal-time search counts (640 vs 1,600, then 270 vs 630 over 200–300 games) v6b scored 0.460–0.497 across iterations 4–24 (detailed in [A Bigger Network and Why It Was Not Deployed](/docs/optimization/bigger-network)). Local equal-time matches using actual 2.5 s clocks are also implemented in [`eval_local.py duel`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/eval_local.py#L192-L232).

## The Round-Robin Ladder

When v5 beat V4 39–1 (`cont6`), the V4 reference match saturated and could no longer rank v5's late checkpoints, while the promotion gate only tested the latest model against one champion. Commit [`e82d5c5`](https://github.com/sungyongcho/gomoku/commit/e82d5c5) introduced [`ladder.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/ladder.py#L29-L182), the standalone CLI [`scripts/ladder.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/ladder.py#L35-L90), checkpoint averaging in [`average_state_dicts`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/state_dict_utils.py#L41-L65), and [`run_iteration_ladder`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/pipelines/run_ray.py#L232-L293).

Every `every_iters` iterations, the in-run ladder played a colour-swapped round-robin at 800 searches without noise among four models (`LadderConfig` in `cont7`, `cont8`):

- the latest iteration (`itNNNN`);
- the parameter mean of the last `average_last: 5` iterations (`avgNNNN`, averaging floating-point weights and batch-norm statistics in `float64` while keeping integer buffers from the last checkpoint);
- fixed earlier anchor checkpoints (`anchors: [116, 130]`), placing iterations from across the run on one shared scale.

[`fit_ratings`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/ladder.py#L29-L60) computes Bradley–Terry Elo ratings over 500 minorisation iterations. It adds one virtual draw (0.5 points each) between every pair of players so an unbeaten model's rating stays finite, updates strengths $\pi_i$, normalizes the geometric mean to 1.0 (centring the ratings at 0), and converts to Elo:

$$
\pi_i^{(t+1)} = \frac{W_i}{\sum_{j \ne i} \dfrac{n_{ij}}{\pi_i^{(t)} + \pi_j^{(t)}}}, \qquad R_i = 400 \log_{10}\!\left(\frac{\pi_i}{\left(\prod_{k=1}^K \pi_k\right)^{1/K}}\right)
$$

In practice, the in-run ladders at iterations 135 (4 opening plies, 10 pairs per pairing = 120 games) and 140 (3 opening plies, 20 pairs per pairing = 240 games) scored every pairing among 116, 130, `itNNNN`, and `avgNNNN` within one game of even (9–11 of 20 at 135, then 19–21 of 40 at 140), while tying up the cluster for 48 to 62 minutes per ladder ([`v5-small-6x96-cont9.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L3-L10)). That slowdown traced to roughly 281,000 denormal float32 weights running at 206–258 ms per position on the two Intel C4 worker nodes versus 7 ms on the AMD C4D nodes (10 ms on Intel once commit [`719fe38`](https://github.com/sungyongcho/gomoku/commit/719fe38) added `torch.set_flush_denormal(True)` to [`play_ladder_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/ladder.py#L77) and [`play_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/reference_match.py#L92)). `cont9` removed the ladder from the training loop and left final checkpoint selection to the standalone `scripts/ladder.py`. Across iterations 116 to 144, [`v6-10x128.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v6-10x128.yaml#L2-L3) notes that a 360-game ladder still did not separate the checkpoints clearly, though [`v6b-10x128-cont1.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v6b-10x128-cont1.yaml#L5-L6) records that after the learning rate dropped from 0.0002 to 0.0001 at iteration 131, iterations 140 and 144 placed above 116 and 130.

## The 900-Game Selection Tournament

At the end of the v5 run, a **900-game selection tournament** ran offline across candidate checkpoints and selected **iteration 144** (`v5-small-6x96` `iteration_0144.pt`) as the model to deploy on Oracle Cloud (`deploy-v5.yaml`, `deploy-v5-pruned.yaml`) and as the fixed reference checkpoint in `v6` and `v6b`. Consistent with the `cont1` note above, iteration 144 placed above the earlier anchors 116 and 130 after the late learning-rate drop; the full per-checkpoint table and exact margins from the 900-game run were not saved in the repository.

## Extra Diagnostic Reports (`replay_report.py`)

Win/loss counts alone do not explain *why* a model loses or separate search failures from network errors. Three commits expanded [`replay_report.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/replay_report.py) to inspect self-play Parquet shards and raw checkpoint policies directly:

- **How games end and raw-policy tactical checks ([`c0dc51e`](https://github.com/sungyongcho/gomoku/commit/c0dc51e))**:
  - [`IterationStats.end_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/replay_report.py#L50-L62) classifies each finished game from its final stored position: `value == 0` counts as `ended_draws`; otherwise, if the final mover's capture score (`p1_pts` or `p2_pts`) is at least `CAPTURE_GOAL - 1` (4), the game counts as `capture_win`, else `five_win`.
  - [`tactics`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/replay_report.py#L211-L270) evaluates the raw policy head **without MCTS** on up to 300 (`--tactic-samples`) positions per category from the latest iteration (`>= 6` stones): `win_top1` and `win_mass` when the side to move has an immediate winning move, `block_top1` and `block_mass` when the opponent threatens an immediate win, and `forbidden_mass` versus `forbidden_uniform` on double-three points. In `v5-small-6x96-cont4.yaml`, 8 of 9 local losses to V4 were unblocked fives along the outer line where v5's raw policy placed near 0 probability on the block (and `value` read +1.0); under `cont5`, outer-line five blocking in the raw policy stayed at 0.62–0.63 top-1.
- **White's first-reply distance ([`4e23926`](https://github.com/sungyongcho/gomoku/commit/4e23926))**:
  - [`IterationStats.add`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/replay_report.py#L92-L99) records the Chebyshev distance $\max(|x_B - x_W|,\, |y_B - y_W|)$ between Black's first stone and White's first reply when search chose it, reporting `reply_near` (fraction at distance $\le 2$) and `reply_dist` (median distance). Before iteration 29, `reply_near` sat at 2%–4%; from iteration 29 onward it jumped to 53%–68% ([`v5-small-6x96-cont.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont.yaml#L14-L15)).
- **Counting games with random openings ([`5b058ac`](https://github.com/sungyongcho/gomoku/commit/5b058ac))**:
  - Once `random_opening_turns > 0` left unstored random stones on the board at the first saved row of a game, checking `stones == 0` stopped detecting game boundaries. [`_starts_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/replay_report.py#L64-L71) detects a new game from `history` continuity (`len(history) < len(previous)` or `history[1:] != previous[:len(history) - 1]`), adjusts `first_player_wins` for the mover's perspective when an odd random opening leaves White to move first (`row["value"] * (1 if player == 1 else -1) > 0`), and restricts `reply_distance` to games with `_start_stones < 2` so random two-stone openings are excluded.

For local checkpoints, [`eval_local.py opening`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/eval_local.py#L65-L114) also reports White's first reply, Chebyshev distance, empty/first-stone value, policy entropy relative to uniform, top-move visit count, and tied top visits against four fixed first stones: `(9, 9)`, `(3, 3)`, `(15, 9)`, and `(0, 0)`.

## The Move Cap That Was Added and Reverted

Because captures remove pairs of stones and leave empty squares behind, a Gomoku game under capture rules can cycle without filling the 19×19 board. On 2026-11-08, commit [`e92f98a`](https://github.com/sungyongcho/gomoku/commit/e92f98a) added `max_plies: int = 200` to `ReferenceMatchConfig` and [`reference_match.play_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/reference_match.py#L100) so games reaching 200 plies ended as draws and capture loops could not stall training. Four minutes later, commit [`65f3fb7`](https://github.com/sungyongcho/gomoku/commit/65f3fb7) reverted that cap so reference games play to their natural end (up to the `2 * 361 = 722`-ply safety bound).

When the round-robin ladder hit the cluster stall problem at iteration 135, a move cap returned there instead of in reference matches: 12 of the 120 ladder games ran 20 to 48 minutes each even though no self-play game in iterations 131–135 exceeded 65 plies, so `v5-small-6x96-cont8.yaml` lowered `ladder.max_plies` from 400 to 80 (`v5-small-6x96-cont8.yaml#L11-L13`) and used the saved time to double the ladder from 10 to 20 openings per pairing.
