# Running the Training Cluster

Training the `v5` (`6x96`) and `v6` / `v6b` (`10x128`) models used a Ray cluster on Google Cloud sized to fit a 100-vCPU quota: one `g2-standard-16` GPU head node paired with 11 CPU worker VMs across `europe-west2` (after a 3-worker pilot in `europe-west4`), built from a shared `python:3.13.18-slim-trixie` base and pinned `constraints.txt` so head and worker versions cannot drift apart.

Most of the engineering time between [`eaf7fa7`](https://github.com/sungyongcho/gomoku/commit/eaf7fa7) and [`853b0fe`](https://github.com/sungyongcho/gomoku/commit/853b0fe) went into removing bottlenecks and fixing distributed failures discovered during the runs: switching self-play off remote GPU inference actors into in-worker `bfloat16` plus GPU-node workers, excluding host-built native `.so` binaries from containers, capping in-flight async MCTS batches to stop virtual loss from flattening root visit counts, propagating remote inference errors so search cannot hang, flushing denormals in CPU `float32` evaluation games, plus scripts for tearing the cluster and its resources down. For the training runs themselves, see [A Smaller Network Trained Properly](/docs/optimization/training-v5) and [A Bigger Network and Why It Was Not Deployed](/docs/optimization/bigger-network).

## Cluster Layout and the 100-vCPU Quota

In the original architecture documented in [Training Pipeline and GCP Infrastructure](/docs/alphazero/training-pipeline) and [Search Engine Architecture](/docs/alphazero/search-engine-architecture), CPU self-play workers sent every MCTS evaluation batch over Ray to GPU inference actors on the head node. Scaling that layout up for `v5` required packing as many self-play slots as possible under two Google Cloud quotas while avoiding saturation on the single L4 GPU.

### Moving From Remote GPU Actors to In-Worker `bfloat16` and Head GPU Workers

Pilot measurements on `2026-11-07` ([`v5-small-6x96-local-pilot.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-local-pilot.yaml#L1-L7)) showed that remote GPU inference actors saturated around `~770` inference requests/s on the head node regardless of how many self-play workers ran, limiting the 3-worker pilot to `~6,200` positions/s (`~6,000` noted in [`v5-small-6x96.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96.yaml#L4-L5)).

Commits [`bb34c62`](https://github.com/sungyongcho/gomoku/commit/bb34c62) and [`c146b1f`](https://github.com/sungyongcho/gomoku/commit/c146b1f) eliminated that RPC bottleneck by moving leaf evaluation inside each self-play worker:

- **In-worker `bfloat16` inference**: [`LocalInference`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/inference/local.py#L9-L93) wraps forward passes in `torch.autocast(..., dtype=torch.bfloat16)` when `local_dtype: bfloat16` is set and converts outputs back to `float32` for C++ MCTS. It sets `prefers_sync = True`, so [`CppSearchStrategy._run_native_mcts`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/sequential/cpp_strategy.py#L88-L96) calls `_run_sync_batch_mcts` instead of `_run_async_mcts`, avoiding any per-batch round trip through the Ray object store.
- **GPU-node self-play workers**: [`RayAsyncRunner._create_workers`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/runners/ray_runner.py#L175-L190) spawns `gpu_workers` extra `RaySelfPlayWorker` actors each requesting `num_gpus = gpu_worker_gpu_total / gpu_workers`. Because Ray exposes a GPU only to actors that request one, those workers pin directly to the head node's L4, and [`RaySelfPlayWorker.__init__`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/runners/workers/ray_worker.py#L45-L54) places each worker's model on `"cuda"` (or `"cpu"` on the worker VMs) with `torch.set_num_threads(1)`.
- **Dynamic chunk queue across heterogeneous speeds**: Head GPU workers evaluate batches much faster than CPU worker slots, and games vary in length. In [`RayAsyncRunner.run`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/runners/ray_runner.py#L519-L545), the driver queues two game chunks per worker up front and refills the next chunk via `ray.wait(..., num_returns=1)` as each finishes, so GPU workers naturally absorb more games per iteration instead of waiting at a static split.

## One Python Base Image for Head and Workers

Ray enforces strict compatibility between the head and worker environments: it rejects any worker whose Python `major.minor.patch` version differs from the head's, and mismatched third-party package versions across nodes can break pickled object serialization and RPC payloads. During an earlier build (`25e6400`), Ubuntu's `deadsnakes` PPA bumped the GPU image to Python 3.13.18 while the CPU image remained on 3.13.11, preventing workers from joining the cluster.

Commit [`bc677d9`](https://github.com/sungyongcho/gomoku/commit/bc677d9) unified both training images around a single pinned Python image and a build-time version check:

- **Identical official base**: Both [`Dockerfile.py313-cu134`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/image/Dockerfile.py313-cu134#L13-L16) and [`Dockerfile.py313-cpu`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/image/Dockerfile.py313-cpu#L7-L8) start from `ARG PYTHON_IMAGE=python:3.13.18-slim-trixie`.
- **Shared package constraints**: Both Dockerfiles copy [`constraints.txt`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/image/constraints.txt#L1-L94) to `/opt/constraints.txt` and export `PIP_CONSTRAINT=/opt/constraints.txt`, pinning `ray==2.60.0`, `torch==2.15.0` (which admits both `+cpu` and `+cu134` wheels), and 83 shared dependencies (85 distributions total).
- **Pre-push version diff gate**: Each image runs [`image_versions.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/image/image_versions.py#L1-L71) and exports `/image-versions.txt` into a minimal `scratch` target named `versions`. The script strips `+cpu`/`+cu134` local tags from `torch` and excludes `SKIP` packages (`gmk-alphazero`, `pip`, `wheel`) plus `GPU_ONLY` CUDA/Triton wheels and packages whose only dependents are CUDA wheels. Before pushing either image, [`restart_cluster.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/cluster/restart_cluster.sh#L187-L206) invokes [`check_image_versions.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/image/check_image_versions.sh#L18-L39) to build both `versions` targets and fail via `diff -u` if any version diverges.

Upgrading Ray to 2.60.0 in [`7df7562`](https://github.com/sungyongcho/gomoku/commit/7df7562) added two matching runtime pins: setting `-e RAY_AUTH_MODE=disabled` in [`cluster_v5.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/cluster/cluster_v5.yaml#L29-L34) so Ray `2.59+` token auth does not block worker nodes lacking a head token, and exporting `RAY_UP_enable_autoscaler_v2=0` in [`restart_cluster.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/cluster/restart_cluster.sh#L256-L258) to keep Ray's v1 Docker autoscaler behavior.

## Failures and Fixes Along the Way

### Host Native Extensions Shadowing Container Builds (`glibc` Mismatch)

When the C++ pybind11 extension (`gomoku_cpp`) was built locally on a developer host and left inside `alphazero/gomoku/cpp_ext/*.so`, `COPY . /app` inside the Dockerfiles copied those host-compiled `.so` files straight into `/app/gomoku/cpp_ext/`. Meanwhile, `pip install ".[ray]"` compiled a clean extension for the container's `glibc` into `/opt/venv/lib/python3.13/site-packages/...`.

Because the container's `WORKDIR` is `/app`, Python adds `/app` at the front of `sys.path` ahead of `site-packages`. Importing `gomoku.cpp_ext` therefore loaded the host `.so` first, which failed against the Debian Trixie container's `glibc` whenever the host carried a different `glibc` version. Commit [`7e77405`](https://github.com/sungyongcho/gomoku/commit/7e77405) excluded local native binaries from the Docker build context in [`alphazero/.dockerignore`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/.dockerignore#L18-L19):

```gitignore
# alphazero/.dockerignore:18-19
# Local native builds link against the host glibc; the image builds its own into the venv.
gomoku/cpp_ext/*.so
```

### Slow Remote Inference Flattening Root Visit Counts

While running remote GPU inference actors during the early `v5` setup, [`MctsEngine::RunAsyncSimulation`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L500-L578) had no cap on how many inference batches could be in flight at once. Under fast in-process evaluation, batches drain immediately so the queue stays near 1 batch. Under slow remote RPCs over the cluster network, the C++ loop dispatched nearly all `num_simulations` before the first batch's policy/value reply returned.

The reason this flattens root visits follows directly from [`MctsEngine::CalculateUcb`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L807-L828). During selection, every node along an in-flight simulation's path receives `virtual_loss += 1` ($L$), while completed visits remain $N = 0$ (or small) until RPCs return:

$$
\text{UCB}(s, a) = Q(s, a) + c_{\text{puct}} \cdot P(s, a) \cdot \frac{\sqrt{N_{\text{parent}} + L_{\text{parent}} + 1}}{1 + N_{\text{child}} + L_{\text{child}}}
$$

$$
Q(s, a) = \begin{cases}
-\dfrac{W_{\text{child}} + L_{\text{child}}}{N_{\text{child}} + L_{\text{child}}} & \text{if } N_{\text{child}} > 0, \\[8pt]
\dfrac{W_{\text{parent}}}{N_{\text{parent}}} - r_{\text{fpu}} & \text{if } N_{\text{child}} = 0 \text{ and } \texttt{fpu\_from\_parent} \text{ and } N_{\text{parent}} > 0, \\[6pt]
0 & \text{otherwise.}
\end{cases}
$$

Each pending visit on a top-prior move increases $L_{\text{child}}$: if $N_{\text{child}} > 0$, it pulls $Q$ toward $-1$ and shrinks the exploration bonus via $1 + N_{\text{child}} + L_{\text{child}}$; if $N_{\text{child}} = 0$, its denominator doubles to $2$ and selecting the same unexpanded leaf again hits the `duplicate` guard in [`MctsEngine.cpp`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L568-L577). Meanwhile, every untouched move stays at denominator $1$ with zero virtual loss. Without backed-up values to keep search on strong lines, an uncapped async loop exhausts high-prior moves and spreads visits across nearly the entire board.

Commit [`3ab029f`](https://github.com/sungyongcho/gomoku/commit/3ab029f) added `max_inflight_batches: int = 1` across [`MctsConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L155-L157), [`CppSearchStrategy._run_async_mcts`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/sequential/cpp_strategy.py#L155-L162), [`gomoku_bindings.cpp`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/gomoku_bindings.cpp#L286-L289), and [`MctsEngine.cpp`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L548-L554):

```cpp
// alphazero/cpp/src/MctsEngine.cpp:548-554
// 1. Selection Phase. Select only while a batch slot is free: leaves picked while
// earlier results are still out see virtual loss instead of values, so an uncapped
// loop under a slow evaluator spreads the visits over almost every move.
while (sims_dispatched < num_simulations &&
       static_cast<int>(in_flight.size()) < max_inflight_batches &&
       static_cast<int>(current_states.size()) < batch_size)
```

Two regression tests quantify the effect:

- In [`native_async_inflight_test.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/pvmcts/native_async_inflight_test.py#L13-L96) (`9x9` board, 200 simulations, batch 8, peaked logits `[4.0, 2.0, 2.0, 0...]`, 20 polls per reply), uncapped async search visited all 81 legal moves, whereas `max_inflight_batches = 1` matched synchronous batched search at roughly 30 moves visited.
- In [`native_async_test.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/pvmcts/native_async_test.py#L143-L150) (48 simulations with a 50 ms evaluator sleep), `max_inflight_batches = 1` matched sync visits identically while `max_inflight_batches = 8` visited more than 10 additional moves.

### Remote Inference Errors Hanging Async Search

Before commit [`147dee5`](https://github.com/sungyongcho/gomoku/commit/147dee5), the Python `async_checker` callback passed into `run_mcts_async_encoded` caught exceptions raised by `ray.get(ref)` while deleting the batch handle from `inflight_refs`. Because the failed batch was never returned to C++ and no exception escaped back into [`RunAsyncSimulation`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L545), `sims_completed < num_simulations` stayed true indefinitely, hanging the worker forever on an inference actor crash.

Commit [`147dee5`](https://github.com/sungyongcho/gomoku/commit/147dee5) removed exception swallowing in [`cpp_strategy.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/sequential/cpp_strategy.py#L140-L171) so actor errors propagate out of `run_mcts_async_encoded` into the `finally:` block, which cancels remaining Ray object references (`test_async_inference_errors_stop_the_search_instead_of_hanging` in [`native_async_test.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/pvmcts/native_async_test.py#L138-L140)). The same change added `.detach().float().cpu().numpy()` because `bfloat16` actor outputs have no direct NumPy buffer protocol.

### Evaluation Games Slowed by Denormal Weights

Although self-play workers ran in `bfloat16`, in-run evaluation ladders and reference matches ran single-threaded `float32` CPU inference across all workers and joined at a synchronous barrier. Once `v5` (`6x96`) accumulated roughly 281,000 subnormal (denormal) weights from Adam L2 decay, the two Intel `C4` nodes (12 of the cluster's 84 CPU worker vCPUs) stalled in microcode assists on subnormal operations, holding the entire 100-vCPU cluster for 48 to 62 minutes on the ladders at iterations 135 and 140 ([`v5-small-6x96-cont9.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L3-L10)):

## Teardown Tooling

The repository holds the teardown tooling below; it does not record which of these steps ran or when. One related note sits in [`v5-small-6x96-cont5.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont5.yaml#L17): the storage bucket was deleted on `2026-11-09`, during the run, and resuming from that config means restoring a backup into a bucket of the same name or changing the run paths.

- **Cluster and project purge script**: [`purge_gcp.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/cluster/purge_gcp.sh#L98-L170) tears down the Ray cluster instances (`ray-<cluster>-*`), the head GPU reservation, the Ray firewall rules (`ray-allow-internal`, home access rules, and `ray-allow-iap-ssh`), the Cloud NAT gateway and router, the Artifact Registry repository, the GCS training bucket, optionally the entire training GCP project (`--delete-project`), and revokes/removes local `gcloud` credentials (`~/.config/gcloud`).
- **Network org-policy revert**: [`02_setup_network.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/bootstrap/02_setup_network.sh#L98) documents deleting the project-level `compute.vmExternalIpAccess` org-policy override once training is finished.
- **Separate serving VM cleanup**: Once serving moved to Oracle Cloud (see [Serving on a 2-Core Arm Instance](/docs/optimization/free-arm-hosting)), [`deploy/alphazero/teardown.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero/teardown.sh#L77-L122) covers removing the old V4 GCP serving VM, its static IP, firewall rules, and deploy container images, alongside [`deploy/purge_local_gcloud.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/purge_local_gcloud.sh#L47-L95) for revoking local `gcloud` state, SSH keys, and Docker Artifact Registry credential helpers.
