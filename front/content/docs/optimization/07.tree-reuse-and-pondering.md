# Using the Opponent's Time

Every move request from the frontend carries the entire board and no game identifier. Before commit [`f416558`](https://github.com/sungyongcho/gomoku/commit/f416558), the AlphaZero server treated every request in isolation: it reconstructed the position, grew a fresh MCTS tree from scratch for 2.5 seconds (completing a median of 668 searches with the pruned `6x96` network on two Arm Neoverse-N1 cores), picked a move, and deleted the entire tree before returning the answer. Everything searched along the opponent's likely replies was thrown away on every turn.

Commit [`f416558`](https://github.com/sungyongcho/gomoku/commit/f416558) changed serving in two ways: each WebSocket connection keeps its native C++ search tree between moves to carry prior simulations forward, and a single background thread continues searching the post-move position while the opponent thinks, bounded by a 120-second time cap and a shared 50,000-node cap. On the Oracle Cloud `VM.Standard.A1.Flex` instance, full-game self-play checks over two per-colour connections raised the median searches behind a move from 668 to 1,468 with tree reuse alone, 6,363 when the opponent thinks for 5 seconds, and 13,859 at 15 seconds, while keeping maximum answer times below 2.6 seconds inside the 3-second target (see [Why This Section Exists](/docs/optimization/intro) and [Answering by the Clock](/docs/optimization/time-limited-serving)).

## From Stateless Requests to Per-Connection Trees

In the stateless serving path, [`_handle_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/websocket.py#L119-L143) converted the incoming JSON payload into a `GameState` and called [`AlphaZeroEngine.get_best_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/engine.py#L149-L175), which entered [`MctsEngine::RunSimulationEncoded`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L255-L274) and called `ResetRoot(root_state)`. That kept every request self-contained, at the cost of repeating the search from zero on every ply.

With `mcts.reuse_tree: true` (set in [`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L27-L29); defaults to `false` in [`MctsConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L140-L142)), the server treats one WebSocket connection as one game. When a client connects to `/ws` or `/ws/debug`, [`_serve`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/websocket.py#L258-L270) calls [`AlphaZeroEngine.open_session`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/engine.py#L108-L112) to allocate a [`SearchSession`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L118-L138) holding its own native `MctsEngine` instance, and frees it in `finally` via [`session.close()`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L224-L228). [`AlphaZeroEngine.__init__`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/engine.py#L84-L94) enables `reuse_tree` only when `use_native` is active and `batch_infer_size <= 1`, matching the single-sample CPU serving path.

Because simulations can now start from an already-populated root, the total search count backing a move becomes the sum of prior visits preserved in the aligned subtree and new simulations run for the current request:

$$
N_{\text{move}} = N_{\text{carried}} + N_{\text{new}}
$$

In [`SearchSession.best_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L165-L191), this split is recorded in [`SearchStats`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L39-L57) (`carried`, `new`, `total = carried + new`, and `pondered`) and attached to the move response's `search` field in [`build_move_response`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/protocol.py#L177-L221) for server logs and measurement scripts. In deterministic fixed-count checks ([`test_same_move_as_a_fresh_search_of_equal_size`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_pondering.py#L156-L165) and [`test_continuing_equals_one_longer_search`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L85-L89)), continuing a tree for $N_{\text{new}}$ simulations yields the exact same visit counts as a single fresh search of $N_{\text{carried}} + N_{\text{new}}$ simulations.

## Keeping and Matching the Subtree

Keeping a tree across turns requires two transitions: moving the root down to the move the engine just played, and later verifying whether the next incoming request continues from that position.

### Advancing After an Answer

In [`_handle_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/websocket.py#L174-L181), once the JSON response has been sent and the position is not terminal, the server calls [`SearchSession.commit_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L193-L199). That delegates to [`MctsEngine::AdvanceRoot`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L116-L132) and `AdvanceToChild`, which detach the child corresponding to the played move `action`, delete the old root (freeing all sibling subtrees recursively), advance `root_state_` with `core_->apply_move`, recount `node_count_`, and leave the tree rooted at the post-move position where it is the opponent's turn to play.

### Matching the Next Request

When the next move request arrives on the connection, [`SearchSession.best_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L164-L168) converts the incoming payload to a `GomokuState` and calls [`MctsEngine::AlignRoot`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L134-L157):

```cpp
// alphazero/cpp/src/MctsEngine.cpp:25-34, 134-157
bool SameState(const GomokuState &a, const GomokuState &b)
{
    return a.next_player == b.next_player
        && a.last_move_idx == b.last_move_idx
        && a.p1_pts == b.p1_pts
        && a.p2_pts == b.p2_pts
        && a.empty_count == b.empty_count
        && a.board == b.board
        && a.history == b.history;
}

int MctsEngine::AlignRoot(const GomokuState &target)
{
    if (root_ == nullptr) {
        return -1;
    }
    if (SameState(root_state_, target)) {
        return root_->visit_count;
    }
    const int move_idx = target.last_move_idx;
    for (std::size_t i = 0; i < root_->moves.size(); ++i) {
        if (static_cast<int>(root_->moves[i]) != move_idx) {
            continue;
        }
        GomokuState next = core_->apply_move(
            root_state_, move_idx % board_size_, move_idx / board_size_, root_->player_to_play
        );
        if (!SameState(next, target)) {
            return -1;
        }
        AdvanceToChild(i, std::move(next));
        return root_->visit_count;
    }
    return -1;
}
```

Because WebSocket requests can come from taken-back moves, edited boards, or older clients without full move history, matching only `last_move_idx` is insufficient ([`test_last_move_alone_is_not_enough`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L136-L144)). `SameState` compares all seven fields of `GomokuState`: `board`, capture points (`p1_pts`, `p2_pts`), side to move (`next_player`), `last_move_idx`, `empty_count`, and the recent-move `history` (up to 5 moves under `history_length: 5`). Every incoming position takes one of four paths:

- **Same position (`SameState(root_state_, target)`)**: The entire kept tree is retained (`carried = root_->visit_count`). This occurs when a single connection asks the engine to play both sides without an intervening human move.
- **Expected or legal reply one move below `root_state_`**: `AlignRoot` applies `target.last_move_idx` to `root_state_`, checks `SameState(next, target)`, promotes that child via `AdvanceToChild` (freeing all other reply branches), and returns `root_->visit_count`. Even if the opponent plays a legal move that had 0 prior visits, `AlignRoot` still matches and creates a 1-node root with `carried = 0` ([`test_unsearched_reply_starts_empty_but_matches`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L75-L82)).
- **Any other position**: If `AlignRoot` returns -1 (two moves ahead, takeback, altered capture points, edited stone, or mismatched `history` as tested in [`test_other_positions_do_not_match`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L103-L133)), `SearchSession.best_move` calls `reset_root(native_state)` to drop the old tree and start fresh with `carried = 0`.
- **Explicit reset or new connection**: A `{"type": "reset"}` WebSocket message ([`websocket.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/websocket.py#L249-L253)) calls `session.reset()`, clearing the tree and stopping any active background search for that session; a new WebSocket connection creates a fresh `SearchSession` with no tree.

## Creating Nodes on First Visit and Capping Memory

Before [`f416558`](https://github.com/sungyongcho/gomoku/commit/f416558), `MctsEngine::ExpandAtLeaf` allocated a `new MctsNode()` for every legal move immediately when a leaf was evaluated. On a 19×19 board with up to 361 legal moves per position, a single leaf expansion created hundreds of `MctsNode` objects that might never receive a single visit. When every tree lived for a single 200- to 600-simulation request and was deleted right away, that excess allocation did not accumulate across turns. Once trees persist across moves and can ponder for tens of thousands of simulations, creating `~300+` unvisited nodes per expansion multiplies memory usage and tree-deletion time by more than an order of magnitude.

Commit [`f416558`](https://github.com/sungyongcho/gomoku/commit/f416558) moved node creation to first visit in [`MctsNode`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/include/MctsEngine.h#L12-L30) and [`MctsEngine::Select`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L678-L717):

- [`MctsEngine::ExpandAtLeaf`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L784-L790) now stores only the legal moves (`std::vector<int16_t> moves`) and their softmax priors (`std::vector<float> priors`) directly on the expanded leaf, leaving `children` empty.
- Inside [`MctsEngine::Select`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L690-L716), `CalculateUcb` treats a missing `MctsNode *` as `visit_count = 0` and `virtual_loss = 0`. Only when search actually descends into a move does `Select` initialize `node->children` (if empty) to null pointers and allocate a `new MctsNode()` for `best_index`, incrementing `node_count_`.

Because every simulation through a node allocates at most one child node below it ([`test_subtree_matches_the_search_it_came_from`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L92-L100)), both memory footprint and recursive freeing time scale with the number of completed simulations rather than the branching factor. On a 19×19 board, each node takes `4 to 5 KB` ([`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L34), [`MctsConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L146-L148)).

To bound RAM across all open connections, [`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L34) sets `mcts.ponder_max_nodes: 50000` (roughly 250 MB of tree nodes across all kept trees combined). Whenever [`Ponderer.start`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L88-L95) prepares a background search for a session, it calculates the remaining headroom left by all other registered sessions:

$$
N_{\text{limit}}(\text{session}) = N_{\text{max}} - \sum_{s \neq \text{session}} N_{\text{nodes}}(s)
$$

If `session.node_count >= node_limit`, background pondering does not start (`return False`, tested in [`test_node_cap_counts_every_kept_tree`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_pondering.py#L351-L363)). Otherwise `node_limit` is passed as `max_nodes` to [`MctsEngine::ContinueSimulationEncoded`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L297-L299), which exits before starting a simulation once `node_count_ >= max_nodes`. Timed answer searches pass `max_nodes = 0` (uncapped), so a client's 2.5-second move search always runs even when kept trees already sit at the ponder cap.

## Searching While the Opponent Thinks

With `mcts.ponder: true` (which requires `mcts.reuse_tree: true`, enforced by [`MctsConfig._check_pondering`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L163-L171)), the server uses the idle time between sending a move and receiving the opponent's reply to deepen the subtree below the move it just played.

### One Background Search at a Time and Its Stop Conditions

The process-wide [`Ponderer`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L60-L116) allows **at most one** background daemon thread (`alphazero-ponder`) at any time. Running multiple concurrent searches or overlapping a background search with an active move request would split the instance's two Arm cores and slow down the timed search.

After [`SearchSession.commit_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L193-L214) advances the root, `Ponderer.start` calls `session.native.clear_stop()` and runs `ContinueSimulationEncoded` with `num_simulations = 2_000_000_000`, `time_limit_s = 120.0`, `max_nodes = node_limit`, and `stoppable = True`. Four events terminate that background search:

1. **Next move request on any connection**: [`_handle_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/websocket.py#L128-L131) calls `engine.stop_pondering()`, and `SearchSession.best_move` calls `self._ponderer.stop()`. [`Ponderer.stop`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L106-L115) sets `stop_requested_` via [`RequestStop`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/include/MctsEngine.h#L113-L114) and calls `thread.join()`, stopping the loop right after at most one in-flight leaf evaluation finishes ([`test_stop_does_not_wait_for_the_ponder_limits`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_pondering.py#L295-L306)). Because `stop_requested_` stays latched until `clear_stop()`, even an immediate stop issued before the background thread enters the C++ loop ends it cleanly ([`test_stop_requested_before_the_search_starts_still_ends_it`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L217-L224)), while timed answer searches pass `stoppable = false` so a stale flag can never cut them short ([`test_timed_search_ignores_a_stale_stop_request`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_tree_reuse.py#L227-L231)).
2. **Connection close or `reset` message**: [`SearchSession.close`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L224-L228) calls `ponderer.unregister(self)` (which stops only if this session owns the active ponder thread) and clears the tree; [`SearchSession.reset`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L216-L222) does the same while keeping the connection open.
3. **Time cap (`mcts.ponder_time_limit_s: 120`)**: stops background search on an open, idle connection after 120 seconds ([`test_ponder_stops_at_the_time_limit`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_pondering.py#L319-L325)).
4. **Shared node cap (`mcts.ponder_max_nodes: 50000`)**: stops once total nodes across all kept trees reach `node_limit`.

If background evaluation raises an exception, [`SearchSession.ponder`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L212-L214) catches it and sets `self._ponder_failed = True`; the next `best_move` clears the tree and rebuilds ([`test_failed_ponder_rebuilds_the_tree`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_pondering.py#L372-L387)).

### Taking Stop Time Out of the Search Limit

Stopping the background thread requires waiting for its in-flight leaf forward pass to finish and calling `AlignRoot` before the next move search begins. To prevent that overhead from eating into the 0.5-second margin inside the 3-second response target, [`_handle_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/websocket.py#L128-L142) captures `start_ns = time.perf_counter_ns()` *before* calling `engine.stop_pondering()`, and [`SearchSession.best_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L173-L176) subtracts all elapsed time since arrival from `time_limit_s`:

```python
# alphazero/server/session.py:173-176
time_limit_s = float(cfg.time_limit_s or 0.0)
if time_limit_s > 0.0 and started is not None:
    spent = time.perf_counter() - started
    time_limit_s = max(time_limit_s - spent, _MIN_TIME_LIMIT_S)
```

In equation form:

$$
T_{\text{limit, effective}} = \max\!\left(T_{\text{limit}} - (t_{\text{now}} - t_{\text{started}}),\; 0.001\text{ s}\right)
$$

Here `_MIN_TIME_LIMIT_S = 0.001` avoids passing 0.0 into C++, where 0.0 means unlimited time ([`test_spent_time_comes_out_of_the_search_budget`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_pondering.py#L216-L235)); on an unsearched root, C++ still guarantees at least one simulation before exiting. Because the timed search starts only after `thread.join()` returns, it keeps both Neoverse-N1 cores to itself. On early moves on the Oracle A1 host, new searches completed during the answer window stayed virtually unchanged: `704, 683, 684, 707` with `ponder` enabled versus `721, 709, 681, 701` without it ([`deploy/alphazero-oracle/README.md`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L134-L136)).

## Full-Game Measurements on the Arm Instance

All serving measurements were collected on the Oracle Cloud `VM.Standard.A1.Flex` instance (2 Arm Neoverse-N1 cores, 12 GB RAM, `aarch64`) running `v5` iteration 144 pruned ([`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml)) with static `int8` ONNX inference on 2 threads (`ALPHAZERO_INFER_THREADS=2`) ([`deploy/alphazero-oracle/README.md`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L107-L143)).

### Measurement Setup (`--connections 2`)

Asking the server for both Black and White moves over a single WebSocket connection would test a degenerate case: the engine's own previous reply is already `root_state_`, so `AlignRoot` would keep the entire tree on every turn, which never happens against a real opponent. Commit [`f416558`](https://github.com/sungyongcho/gomoku/commit/f416558) updated [`smoke_game.py`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/smoke_game.py#L67-L147) with `--connections 2` and `--think-s`:

```sh
.venv/bin/python ../deploy/alphazero-oracle/smoke_game.py --url ws://127.0.0.1:18080/ws \
  --connections 2 --think-s 5
```

Each colour opens its own WebSocket connection (`sockets[ply % 2]`), so each connection sees its own move followed by the opponent's reply. Before sending the next request, the client sleeps for `--think-s` seconds to give the waiting connection's background search time to run. One full self-play game (`max_plies = 200`, running until terminal) was played per row. Reported search counts are **medians** across all moves after each connection's first (`searches[connections:]`), both because each connection's opening move has no kept tree yet and because near the end of a game most MCTS simulations hit terminal positions without calling the neural network, pushing late-game counts into the tens of thousands.

### Measured Results

With `03_bench_search.sh` giving a 668-search median on a fresh tree in 2.5 seconds, the full-game runs measured:

| Setting | Searches behind a move | Carried over | New | Answer mean / max | Container memory peak |
| --- | --- | --- | --- | --- | --- |
| no kept tree | 668 (the benchmark's median) | 0 | 668 | 2.52 s / 2.59 s | 262 MB |
| `reuse_tree` | 1,468 | 646 | 812 | 2.42 s / 2.53 s | 262 MB |
| `reuse_tree` + `ponder`, opponent answers at once | 1,468 | 651 | 799 | 2.42 s / 2.56 s | 263 MB |
| `reuse_tree` + `ponder`, opponent thinks 5 s | 6,363 | 5,303 | 1,044 | 2.51 s / 2.53 s | 307 MB |
| `reuse_tree` + `ponder`, opponent thinks 15 s | 13,859 | 12,484 | 977 | 2.51 s / 2.51 s | 415 MB |

Because each column reports an independent median across moves, `median(total)` differs slightly from `median(carried) + median(new)`.

### What These Measurements Do Not Show

1. **Self-play upper bound on carried-over searches**: In every row above, the opponent is the same `v5` pruned engine. It therefore replies with moves inside the kept tree's top predicted lines far more often than a human player would. The `carried over` medians (646, 651, 5,303, and 12,484) are an upper range for real games. An unexpected human reply still keeps whatever visits had already been spent below that move (or starts at 0 if that reply was never visited).
2. **One game per condition**: Each row in the table comes from a single self-play game on the instance.
3. **Playing strength gain not measured**: No head-to-head match or SPRT evaluation was run comparing `reuse_tree` + `ponder` against fresh-tree serving, so the Elo or win-rate gain from those extra searches is unmeasured.

For how the server image, static `int8` export, and Cloudflare routing run on this instance, see [Serving on a 2-Core Arm Instance](/docs/optimization/free-arm-hosting).
