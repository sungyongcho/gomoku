# Why This Section Exists

The [Minimax](/docs/minimax/intro) and [AlphaZero](/docs/alphazero/intro) sections document the project as it was written by hand. This section documents a second, week-long round of work from 6 to 13 November 2026 (commits `33397d3` to `f416558`) with a single engineering goal: keep the AlphaZero engine answering within 3 seconds per move while moving it off a paid 4-vCPU Google Cloud machine onto Always Free 2-core Arm hosting. The result: hosting cost fell to zero, and each move is now backed by a median of 668 searches on a fresh tree (1,468 with tree reuse) instead of the fixed 200 the paid machine ran, while answers stayed inside the 3-second target in the measured games.

All of the optimization work in this section was done by AI: an AI coding agent using Anthropic's **Claude Opus 5.5** model designed, implemented, ran, and measured everything covered here, including the code changes, training runs, benchmarks, and deployment. The author's part was only confirming the direction of the work and studying what was implemented in order to learn it.

The pages in this section were written with AI as well: Google's **Gemini 4 Hydrogen** model drafted the text and the interactive diagrams from the repository's commits, configuration files and measurement notes, and **Claude Opus 5.5** checked each number and claim against those sources and corrected what did not match.

## Starting Point and Goal

Until 6 November 2026, the production AlphaZero server ran the V4 champion model (iteration 222): a 12-block, 128-channel ResNet running `num_searches: 200` native C++ MCTS simulations per move on a paid GCP `c2d-standard-4` VM (4 vCPU, 16 GB). On that machine, 200 searches took roughly 2.5 seconds per move (see [C++ Extensions](/docs/alphazero/cpp-extensions) and [Training History & Deployment](/docs/alphazero/deployment)). Every WebSocket request carried the full board state, and the server rebuilt the native state and grew a fresh search tree from scratch on every turn.

The target for this round was zero hosting cost without degrading responsiveness: serve moves within a 3-second target on an Oracle Cloud Always Free `VM.Standard.A1.Flex` instance with 2 Arm Neoverse-N1 cores (`aarch64`) and 12 GB of RAM. The V4 network was never benchmarked on this instance. Even the much smaller 6x96 network, however, reaches only 196 searches in 2.5 seconds there as float32, so a fixed 200 searches with the 12x128 network would not fit the budget. Both the serving loop and the neural network therefore had to be redesigned around the target hardware.

## Fixed Time, Variable Search Budget

The central idea connecting every page in this section is simple: **fix the move clock, not the simulation count**. By stopping MCTS at a 2.5-second time limit (`time_limit_s: 2.5`, leaving 0.5 seconds of margin inside the 3-second move target), response latency stays bounded on any CPU. Once answer time is fixed, playing strength depends on how many quality-weighted searches fit into that window.

For a fresh search tree, the number of simulations completed in the budget $T_{\text{budget}}$ is set by search throughput $r_{\text{search}}$ (simulations per second):

$$
N_{\text{new}} \approx T_{\text{budget}} \cdot r_{\text{search}}, \qquad r_{\text{search}} \approx \frac{1}{t_{\text{tree}} + t_{\text{infer}}}
$$

Here $t_{\text{tree}}$ is the C++ selection, expansion, rule-checking, and backup overhead per simulation, and $t_{\text{infer}}$ is the CPU neural-network forward-pass time for a leaf state (with `batch_infer_size: 1` during serving). Because native C++ already handles tree operations in tens of microseconds per simulation, CPU serving throughput is dominated by $t_{\text{infer}}$. When the server also preserves the search tree between turns on a WebSocket connection and keeps searching while the opponent thinks, the effective search count backing a move becomes:

$$
N_{\text{move}} = N_{\text{carried}} + N_{\text{new}}
$$

where $N_{\text{carried}}$ is the number of prior simulations already rooted at the incoming position.

Every optimization in the pages that follow acts on one of two levers in those equations:

1. **Increase $N_{\text{move}}$ on two Neoverse-N1 cores** — lower $t_{\text{infer}}$ through static `int8` ONNX Runtime quantization, shrink the ResNet from `12x128` to `6x96`, prune residual-block channels that weight decay drove to zero, and carry trees across moves with background pondering.
2. **Increase the value of each simulation** — train the smaller `6x96` network properly from scratch, measure strength without first-player bias, and test whether a larger `10x128` network plays stronger when both models get the same 2.5 seconds on the Arm CPU.

## How Results Are Reported

Every page in this section follows one reporting rule: each measurement states **what was measured, on which hardware, and over how many games**, and **negative or inconclusive results are kept** alongside the changes that shipped.

For example, the larger `10x128` network (`v6b`) beat `v5` at equal simulation counts (0.540 at 1,600 searches each), yet scored only 0.46 to 0.50 over iterations 16 to 32 when each model received its actual 2.5-second Arm search budget (270 searches against 630), so it was not deployed. Likewise, a six-setting search sweep (0.49 to 0.505 over 400 games each) and a paused distillation attempt are recorded as null or incomplete results rather than omitted. Where a measurement covers only one self-play game per condition — as in the tree-reuse and pondering benchmarks on the Arm instance — the pages state that limit explicitly.
