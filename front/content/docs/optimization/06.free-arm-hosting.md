# Serving on a 2-Core Arm Instance

Moving the AlphaZero serving backend off a paid 4-vCPU GCP VM (`c2d-standard-4`) onto an Oracle Cloud Always Free `VM.Standard.A1.Flex` instance (2 Arm Neoverse-N1 cores, `aarch64`, 12 GB RAM, Canonical Ubuntu 24.04) reduced hosting cost to zero while keeping every move inside the 3-second response target.

Unlike the earlier GCP deployment (see [Training History & Deployment](/docs/alphazero/deployment)), the Oracle A1 setup ([`c6267df`](https://github.com/sungyongcho/gomoku/commit/c6267df), [`deploy/alphazero-oracle/`](https://github.com/sungyongcho/gomoku/tree/f416558/deploy/alphazero-oracle)) sizes the neural network to the target Arm cores before deploying, builds its `aarch64` container image directly on the VM, verifies both raw search throughput and a full WebSocket game over an SSH tunnel, and restricts port 8080 to Cloudflare's IPv4 ranges behind a path-routing Worker.

## Always Free Quota and Its Design Consequences

An Oracle Cloud tenancy receives a monthly Always Free A1 allowance of 1,500 OCPU hours and 9,000 GB hours ([`deploy/alphazero-oracle/README.md`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L28-L32)):

$$
H_{\text{OCPU}} = n_{\text{OCPU}} \cdot T_{\text{month}}, \qquad H_{\text{mem}} = M_{\text{GB}} \cdot T_{\text{month}}
$$

For a full 31-day month ($T_{\text{month}} = 744\text{ h}$), a single `VM.Standard.A1.Flex` instance with $n_{\text{OCPU}} = 2$ and $M_{\text{GB}} = 12\text{ GB}$ consumes:

$$
\begin{aligned}
H_{\text{OCPU}} &= 2 \times 744 = 1{,}488 \le 1{,}500\text{ OCPU-h} \\
H_{\text{mem}} &= 12 \times 744 = 8{,}928 \le 9{,}000\text{ GB-h}
\end{aligned}
$$

Over a 30-day month ($720\text{ h}$), the same VM uses $1{,}440$ OCPU hours and $8{,}640$ GB hours. Either way, one 2-OCPU, 12-GB instance running all month consumes almost the entire tenancy quota; adding a second A1 instance in the same tenancy triggers Pay As You Go billing.

That hardware ceiling drives three deployment decisions in [`docker-compose.yml`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/docker-compose.yml#L12-L35) and [`alphazero_oracle_env_config.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/alphazero_oracle_env_config.sh#L34-L38):

- **Dedicated single-service host**: The instance runs nothing besides `gomoku-alphazero`, leaving both Arm cores to the search engine (`ALPHAZERO_THREADS=2`, `OMP_NUM_THREADS=2`, `TORCH_NUM_THREADS=2`). Memory is capped at `mem_limit: 4g`, well inside the host's 12 GB.
- **Time-bounded CPU search**: With `ALPHAZERO_DEVICE: cpu` and two cores, throughput cannot be bought by scaling up the VM. Serving configs stop MCTS at `time_limit_s: 2.5` so latency stays below 3 seconds regardless of network size (see [Answering by the Clock](/docs/optimization/time-limited-serving)).
- **Self-contained native build**: Rather than provisioning a separate `arm64` build runner or container registry, the host builds its own image directly from synced source, protected by a 2 GB swap file during compilation.

## Choosing the Model on the Target CPU

Because `time_limit_s: 2.5` fixes the search clock, every network size answers within roughly 2.5 seconds; what changes with the model, inference backend, and thread count is how many MCTS simulations fit inside that window:

$$
N_{\text{new}} \approx T_{\text{budget}} \cdot r_{\text{search}}, \qquad r_{\text{search}} \approx \frac{1}{t_{\text{tree}} + t_{\text{infer}}}
$$

Here $T_{\text{budget}} = 2.5\text{ s}$, $t_{\text{tree}}$ is the C++ tree-traversal overhead per simulation, and $t_{\text{infer}}$ is the single-position (`batch_infer_size: 1`) inference latency. Benchmarking on the real serving CPU before committing to a model matters for three reasons:

1. **Architecture mismatch**: Training nodes and the earlier GCP VM run `x86_64`, whereas the serving host uses `aarch64` Arm Neoverse-N1 cores with different cache sizes, memory bandwidth, and SIMD instructions.
2. **Arm `int8` kernels**: Static `int8` ONNX Runtime performance depends on the target CPU's quantized convolution kernels. Throughput ratios between `float32` and `int8`, or between `6x96` and `10x128`, cannot be extrapolated reliably from `x86_64` measurements.
3. **Core-matched thread count**: Pinning ONNX Runtime and PyTorch threads to the actual core count (2 on A1) avoids both under-using the second core and over-subscribing threads across two cores. In [`AlphaZeroEngine._detect_available_cpu_count`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/engine.py#L351-L367), the server inspects `os.sched_getaffinity(0)` and cgroup v1/v2 CPU quotas to respect core limits.

### Pre-Deploy and On-Instance Measurements

Candidate configurations were measured on two Neoverse-N1 cores using [`gomoku/scripts/bench_search.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/bench_search.py#L18-L63). The script loads `AlphaZeroEngine` into a temporary `ONNX_CACHE_DIR`, samples 12 evenly spaced board states from a raw-network self-play game (`_sample_states`), sets `num_searches: 100_000` and `time_limit_s: 2.5`, runs sequential `PVMCTS` (`add_noise=False`) on each position, and reports the median simulation count and maximum elapsed time.

On the deployed host, [`deploy/alphazero-oracle/03_bench_search.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/03_bench_search.sh#L23-L44) runs the same script inside a throwaway `gomoku-alphazero:local` container using the exact served config, checkpoint (`models/champion.pt`), backend, and thread settings:

```bash
# deploy/alphazero-oracle/03_bench_search.sh:27-43
if [ "${STOP_ENGINE}" = true ]; then
  log "Stopping the engine for the measurement..."
  a1_ssh "${COMPOSE} stop alphazero"
fi

log "Searching ${POSITIONS} positions with ${A1_CONFIG} (${A1_INFER_BACKEND}, ${A1_THREADS} threads)..."
status=0
a1_ssh "sudo docker run --rm \
  -e ALPHAZERO_INFER_BACKEND='${A1_INFER_BACKEND}' -e ALPHAZERO_INFER_THREADS='${A1_THREADS}' \
  -e OMP_NUM_THREADS='${A1_THREADS}' -e TORCH_NUM_THREADS='${A1_THREADS}' \
  gomoku-alphazero:local python -m gomoku.scripts.bench_search \
  --config '${A1_CONFIG}' --checkpoint models/champion.pt --positions '${POSITIONS}'" || status=$?

if [ "${STOP_ENGINE}" = true ]; then
  log "Starting the engine again..."
  a1_ssh "${COMPOSE} up -d alphazero"
fi
```

Passing `STOP_ENGINE=true` pauses the live serving container for the duration of the benchmark so no active WebSocket session shares the two Neoverse-N1 cores, then restarts the engine afterwards.

The pre-deploy selection measurements and the on-instance `03_bench_search.sh` measurements ([`deploy/alphazero-oracle/README.md`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L11-L24)) are summarized below:

| Model & Checkpoint | Config | Backend | Threads | Searches in 2.5 s | Measurement Context |
| --- | --- | --- | --- | --- | --- |
| `6x96` (v5) | — | `float32 ONNX` | 2 | 196 | Pre-deploy `bench_search` on 2 Neoverse-N1 cores |
| `6x96` (v5) | — | `static int8 ONNX` | 1 | 392 | Pre-deploy `bench_search` on 2 Neoverse-N1 cores |
| `10x128` (v6b) | [`deploy-v6b.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v6b.yaml) | `static int8 ONNX` | 2 | 272 | Pre-deploy `bench_search` on 2 Neoverse-N1 cores |
| `6x96` (v5) | — | `static int8 ONNX` | 2 | 634 | Pre-deploy `bench_search` on 2 Neoverse-N1 cores |
| `6x96` (v5 iter 144, as trained) | [`deploy-v5.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5.yaml) | `static int8 ONNX` | 2 | 613 | On-instance `03_bench_search.sh` |
| `6x96` (v5 iter 144, pruned) | [`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml) | `static int8 ONNX` | 2 | 671 | On-instance `03_bench_search.sh` (668 median in `README` game table) |

On two Neoverse-N1 cores, switching `6x96` from `float32 ONNX` to `static int8 ONNX` lifts the 2.5-second budget from 196 to 634 searches (3.23x), and scaling from 1 to 2 threads raises it from 392 to 634 (1.62x). Static `int8` on both cores therefore became the default in [`alphazero_oracle_env_config.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/alphazero_oracle_env_config.sh#L37-L38). Meanwhile, `6x96` completes 2.33x as many searches in 2.5 seconds as `10x128` (634 vs. 272; see [A Bigger Network and Why It Was Not Deployed](/docs/optimization/bigger-network) for why the larger model lost or tied at those equal-time search counts). After dead residual channels were pruned from v5 iteration 144 (see [What Adam With Weight Decay Did to the Network](/docs/optimization/dead-channels)), the on-instance `03_bench_search.sh` count rose from 613 to 671.

## Host Setup, On-Instance Build, and Deployment

Deployment from a local workstation to the Oracle instance runs through two idempotent scripts and a minimal environment configuration.

### Host Preparation (`01_host_setup.sh` and `host_setup.sh`)

Once the instance is created in the Oracle console (`VM.Standard.A1.Flex`, 2 OCPU, 12 GB, Canonical Ubuntu 24.04 `aarch64`, public IPv4, SSH key), [`deploy/alphazero-oracle/01_host_setup.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/01_host_setup.sh#L16-L25) checks SSH connectivity (`uname -m; nproc; free -h | sed -n 2p`), uploads [`host_setup.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/host_setup.sh#L22-L67), and runs it as `root`:

- **Runtime packages**: Installs `ca-certificates`, `curl`, `rsync`, `python3`, `docker.io`, `docker-compose-v2`, and `iptables-persistent`, enables the `docker` service, and adds the SSH user to the `docker` group.
- **2 GB swap file**: Creates `/swapfile` (`fallocate -l 2G`, mode 600, registered in `/etc/fstab`). Although 12 GB of RAM is ample for serving (`mem_limit: 4g`), the swap file protects on-instance C++ compilation and `pip install` steps from out-of-memory kills.
- **Host firewall (`iptables`)**: Oracle's Ubuntu 24.04 image ships `/etc/iptables/rules.v4` with a trailing `REJECT` rule in the `INPUT` chain, blocking every port except SSH (`tcp/22`) by default. `host_setup.sh` inserts an `ACCEPT` rule for `tcp/8080` at position 6 (before the trailing `REJECT`, falling back to `iptables -I INPUT` if the chain is shorter) and persists it with `netfilter-persistent save`. Docker-published ports traverse `FORWARD`, while the `INPUT` rule keeps host-level listeners reachable as well; source-IP filtering stays in the VCN security list.
- **Build directory**: Creates `~/build` owned by the SSH user so `rsync` can write without root privileges.

### On-Instance `aarch64` Image Build and Deploy Options

[`deploy/alphazero-oracle/02_deploy_alphazero.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/02_deploy_alphazero.sh#L27-L66) builds the container image natively on the Arm host rather than cross-compiling on an `x86_64` workstation or pushing through a container registry (`deploy/alphazero/02_deploy.sh` previously relied on GCP Artifact Registry). Building on the VM avoids QEMU/cross-compilation toolchains and removes registry infrastructure from the deployment path, while Docker layer caching keeps subsequent redeploys fast after the initial multi-minute PyTorch and C++ build on 2 cores.

To prevent stale `x86_64` build artifacts or unrelated checkpoints from polluting the Arm build context, `rsync` explicitly excludes local virtualenvs, native build outputs, and model directories ([`02_deploy_alphazero.sh#L39-L49`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/02_deploy_alphazero.sh#L39-L49)):

```bash
# deploy/alphazero-oracle/02_deploy_alphazero.sh:42-49
a1_rsync \
  --exclude '.venv/' --exclude 'runs/' --exclude 'models/' --exclude 'build/' \
  --exclude 'cpp/build/' --exclude '__pycache__/' --exclude '.pytest_cache/' \
  --exclude '.mypy_cache/' --exclude '.ruff_cache/' --exclude 'gomoku/cpp_ext/*.so' \
  "${ALPHAZERO_SRC}/" "${A1_SSH_TARGET}:${A1_DIR}/src/"
a1_scp "${A1_CHECKPOINT}" "${A1_SSH_TARGET}:${A1_DIR}/src/models/champion.pt"
a1_scp "${SCRIPT_DIR}/docker-compose.yml" "${A1_SSH_TARGET}:${A1_DIR}/docker-compose.yml"
```

On the host, `docker compose` builds [`alphazero/infra/image/Dockerfile.prod`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/image/Dockerfile.prod#L1-L36) from `python:3.13-slim-trixie`. The Dockerfile verifies `ca-certificates >= 20250419+deb13u1` (addressing `DSA-6572-1`), installs `cmake`, `g++`, `ninja-build`, and `curl`, compiles the `cpp/` pybind11 extension natively for `aarch64` via `pip install --no-cache-dir ".[serve,torch-cpu]"` against PyTorch's CPU wheel index, upgrades `certifi>=2026.10.19`, and starts `uvicorn server:create_app --factory --host 0.0.0.0 --port 8080`.

Deployment behavior is controlled through `.env` ([`.env.example#L74-L82`](https://github.com/sungyongcho/gomoku/.env.example#L74-L82), [`alphazero_oracle_env_config.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/alphazero_oracle_env_config.sh#L23-L46)) and shell flags:

| Variable / Flag | Default | Purpose |
| --- | --- | --- |
| `DEPLOY_ALPHAZERO_A1_HOST` | *(required)* | Public IPv4 address of the Oracle A1 instance (validated as IPv4) |
| `DEPLOY_ALPHAZERO_A1_CHECKPOINT` | *(required)* | Local `.pt` checkpoint copied to `src/models/champion.pt` |
| `DEPLOY_ALPHAZERO_A1_CONFIG` | `configs/deploy-v5.yaml` | Serving YAML under `alphazero/` (e.g. `configs/deploy-v5-pruned.yaml`) |
| `DEPLOY_ALPHAZERO_A1_SSH_USER` | `ubuntu` | Remote SSH login user |
| `DEPLOY_ALPHAZERO_A1_SSH_KEY` | *(empty)* | Optional path to SSH private key (`~/.ssh/<key>`) |
| `DEPLOY_ALPHAZERO_A1_PORT` | 8080 | Published host port mapped to container port 8080 |
| `DEPLOY_ALPHAZERO_A1_INFER_BACKEND` | `onnx-static` | Inference backend (`onnx-static` calibrates at container startup) |
| `DEPLOY_ALPHAZERO_A1_THREADS` | 2 | Sets `ALPHAZERO_INFER_THREADS`, `OMP_NUM_THREADS`, and `TORCH_NUM_THREADS` |
| `DO_BUILD` | `true` | `DO_BUILD=false` skips image build and restarts the container |
| `NO_CACHE` | `false` | `NO_CACHE=true` passes `--no-cache` to `docker compose build` |

Because `onnx-static` exports ONNX and runs 100-board calibration at container startup, `02_deploy_alphazero.sh` polls `http://127.0.0.1:${A1_PORT}/` up to 40 times every 3 seconds (120 s max), dumping the last 30 lines of `docker logs gomoku-alphazero` if the health endpoint fails to answer. Offline unit tests in [`deploy/alphazero-oracle/tests/alphazero-oracle-deploy.test.mjs`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/tests/alphazero-oracle-deploy.test.mjs#L54-L108) stub `ssh`, `scp`, and `rsync` to verify target validation, `rsync` exclusions, single-checkpoint upload, missing config/checkpoint rejection, and `STOP_ENGINE` ordering in `03_bench_search.sh`.

## Full-Game Verification Through an SSH Tunnel

HTTP readiness (`GET /`) and single-position throughput (`03_bench_search.sh`) do not verify that the WebSocket protocol, rule enforcement, capture accounting, and 2.5-second clock cutoff hold together across an entire game. Because port 8080 is closed to direct public connections, [`deploy/alphazero-oracle/smoke_game.py`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/smoke_game.py#L67-L150) runs from the operator's workstation through an SSH local port forward:

```bash
ssh -N -L 18080:127.0.0.1:8080 ubuntu@<origin> &
cd alphazero && .venv/bin/python ../deploy/alphazero-oracle/smoke_game.py --url ws://127.0.0.1:18080/ws
```

On every ply (up to `--max-plies`, default 200), `smoke_game.py` builds the exact JSON payload used by the frontend (`board`, `scores`, `nextPlayer`, `goal: 5`, `enableCapture: true`, `enableDoubleThreeRestriction: true`, `lastPlay`, and `recentMoves`), sends it to the running container, and checks the response against its own local `Gomoku(cfg.board, use_native=False)` reference state:

- `answer["type"] == "move"` (no error payload or protocol mismatch).
- The returned coordinate `(x, y)` is present in `state.legal_indices_cache`.
- Applying `(x, y)` locally yields the exact same `board` and `X`/`O` capture `scores` returned by the server.
- Round-trip answer latency `elapsed` does not exceed `--limit-s` (default 3.0 s).

If any check fails, `smoke_game.py` prints the offending ply and exits with status 1. On the Oracle A1 host running `v5` iteration 144 pruned (`static int8`, 2 threads, without tree reuse), one full self-play game averaged 2.52 s per answer with a 2.59 s maximum and 262 MB peak container memory ([`deploy/alphazero-oracle/README.md#L121-L127`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L121-L127)). Passing `--connections 2 --think-s 5` tests separate Black/White connections with simulated opponent think time for tree reuse and pondering, which are covered in [Using the Opponent's Time](/docs/optimization/tree-reuse-and-pondering).

## Cloudflare Worker Routing and Origin Lockdown

Public traffic never connects directly to the A1 instance. Instead, [`deploy/cloudflare/deploy.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/cloudflare/deploy.sh#L140-L230) and [`deploy/cloudflare/cloudflare-worker.js`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/cloudflare/cloudflare-worker.js#L28-L116) split edge TLS termination and path routing from origin compute:

1. **DNS and Worker deployment**: `deploy/cloudflare/deploy.sh` upserts a `DNS only` (grey-cloud, `proxied: false`) `A` record for `alphazero-api.<domain>` pointing to `DEPLOY_ALPHAZERO_IP`, and deploys the `gomoku-ws-router` Worker with `ALPHAZERO_ORIGIN=http://alphazero-api.<domain>:8080`. In [`wrangler.toml`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/cloudflare/wrangler.toml#L9-L14), the Worker attaches only to `<domain>/alphazero/*`, `<domain>/minimax/*`, `<domain>/gomoku`, and `<domain>/gomoku/*`.
2. **Path stripping and WebSocket proxying**: When a browser opens `wss://<domain>/alphazero/ws` (or requests `https://<domain>/alphazero/`), [`_proxyToOrigin`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/cloudflare/cloudflare-worker.js#L28-L58) strips the `/alphazero` prefix, rewrites scheme/host/port to `ALPHAZERO_ORIGIN`, sets the `Host` header to `alphazero-api.<domain>:8080`, preserves `Upgrade: websocket` and request headers/body, and proxies to Uvicorn on port 8080. Afterwards, [`verify_connection.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/cloudflare/verify_connection.sh#L17-L45) checks `https://<domain>/alphazero/` and `wss://<domain>/alphazero/ws`.

On the Oracle Cloud side, the subnet's VCN security list admits only two ingress sources ([`deploy/alphazero-oracle/README.md#L33-L36`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L33-L36)):

- `tcp/22` from the operator's IP address (`/32`) for SSH deployment and tunneled checks.
- `tcp/8080` exclusively from Cloudflare's published IPv4 ranges (`https://www.cloudflare.com/ips-v4`, 15 CIDRs; [`deploy/minimax/00_security_list.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/minimax/00_security_list.sh#L35-L82) automates the identical rule set for the Minimax VCN security list via the OCI CLI).

Restricting port 8080 to Cloudflare's IPv4 ranges is essential for two reasons:

- **No TLS or auth at the origin**: As noted in [`docker-compose.yml`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/docker-compose.yml#L3-L4), the container speaks plain HTTP and plain WebSocket (`ws://`) on port 8080; TLS terminates at Cloudflare, and the Worker reaches `http://<origin>:8080`. Because `alphazero-api.<domain>` is a grey-cloud DNS record, anyone on the internet could otherwise resolve the origin address, bypass Cloudflare's TLS and route policies, and talk to Uvicorn unencrypted.
- **Protecting 2-core compute at the network edge**: Each move request drives both Neoverse-N1 cores at full load for 2.5 seconds. Dropping non-Cloudflare packets in the VCN security list discards port scanners and unproxied floods before they ever reach host `iptables`, Docker, or the engine process.
