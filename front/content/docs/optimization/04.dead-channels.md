# What Adam With Weight Decay Did to the Network

Training the `v5` (`6x96`) network with `torch.optim.Adam` and L2 `weight_decay: 0.0001` drove 132 of its 1,251 convolution filters to zero by iteration 50 and 170 (`~14%`) by iteration 144. The weights left near zero sat in the IEEE 754 `float32` subnormal (denormal) range — roughly 281,000 weights in `v5` — which made CPU `float32` inference on Intel cluster nodes 206 to 258 ms per position instead of 10 ms with denormals flushed.

Two changes addressed both the cause and the already-trained checkpoint in commits [`719fe38`](https://github.com/sungyongcho/gomoku/commit/719fe38) and [`79efde7`](https://github.com/sungyongcho/gomoku/commit/79efde7): evaluation workers call `torch.set_flush_denormal(True)`, new training runs can select decoupled `AdamW` (`training.optimizer: adamw`) with decay restricted to multi-dimensional weights, and [`prune_channels.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/prune_channels.py) slices dead intermediate channels out of a trained checkpoint's residual blocks without altering network outputs.

## Residual Block Structure and Dead Channels

As described in [The Policy-Value Network](/docs/alphazero/neural-network), [`PolicyValueNet`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/model/policy_value_net.py#L61-L150) consists of a `3x3` stem (`start_block`), a tower of `num_resblocks` residual blocks (`res_blocks`), and `1x1` convolutional policy and value heads (`policy_channels = 2`, `value_channels = 1`). In `v5` (`6x96`), the network has 1,251 convolution filters in total: 96 in `start_block`, 576 in `res_blocks.*.conv1`, 576 in `res_blocks.*.conv2`, 2 in `policy_head`, and 1 in `value_head`. In `v6` (`10x128`), the total is 2,691 filters (128 + 10 × 2 × 128 + 2 + 1).

Inside each [`ResBlock`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/model/policy_value_net.py#L152-L185), data passes through two `3x3` convolutions (`conv1`, `conv2`) and two batch-normalization layers (`bn1`, `bn2`) before adding the skip connection `residual`:

```python
# alphazero/gomoku/model/policy_value_net.py:159-184
class ResBlock(nn.Module):
    def __init__(self, num_hidden: int, mid_channels: int | None = None):
        super().__init__()
        mid_channels = mid_channels or num_hidden
        self.conv1 = nn.Conv2d(
            num_hidden,
            mid_channels,
            kernel_size=RESBLOCK_KERNEL_SIZE,
            padding=RESBLOCK_PADDING,
        )
        self.bn1 = nn.BatchNorm2d(mid_channels)
        self.conv2 = nn.Conv2d(
            mid_channels,
            num_hidden,
            kernel_size=RESBLOCK_KERNEL_SIZE,
            padding=RESBLOCK_PADDING,
        )
        self.bn2 = nn.BatchNorm2d(num_hidden)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        """Apply residual block transformation."""
        residual = x
        x = fn.relu(self.bn1(self.conv1(x)))
        x = self.bn2(self.conv2(x))
        x += residual
        x = fn.relu(x)
        return x
```

Note that `start_block`, `policy_head`, and `value_head` pass `bias=False` to `nn.Conv2d`, whereas `ResBlock.conv1` and `ResBlock.conv2` keep PyTorch's default `bias=True`.

A channel becomes **dead** when the training loss stops depending on it and weight decay drives its `conv1` filter, its `bn1` scale (`weight`), and `conv2`'s weights reading that channel toward zero. Once `conv2` multiplies that channel by zero and `bn1` scales it by zero, gradients through the channel vanish and training cannot revive it.

### How Dead Channels Were Measured and Counted

Two sets of counts exist in the project records:

- **Whole-network filter counts**: Checkpoint inspections during training recorded 132 dead filters out of 1,251 in `v5` at iteration 50, 170 of 1,251 (`~14%`) at iteration 144 ([`optimizer.py#L18`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/learning/optimizer.py#L18)), and 497 of 2,691 filters (`~half` of the first convolution in residual blocks `2–9`, with 36% of all weights zero) when `v6` (`10x128`) was pretrained from `v5` games using `Adam` ([`v6b-10x128.yaml#L2-L6`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v6b-10x128.yaml#L2-L6)). The ad-hoc inspection threshold used to report those whole-network filter counts and the `~281,000` denormal-weight count is not checked into the repository.
- **Residual-block channel counting for pruning**: [`prune_state_dict`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/prune_channels.py#L30-L52) inspects the 6 × 96 = 576 intermediate channels inside `res_blocks` and marks channel `c` as alive only if `conv2.weight[:, c, :, :]` has maximum absolute weight at least `threshold = 1e-12`:

```python
# alphazero/gomoku/scripts/prune_channels.py:42
used = state[prefix + "conv2.weight"].abs().amax(dim=(0, 2, 3)) >= threshold
```

Checking `conv2.weight` rather than `conv1.weight` is intentional: `ResBlock.conv1` and `ResBlock.bn1` both have biases, so even a zeroed `conv1` filter can emit a nonzero constant after `bn1` and `ReLU` that `conv2` still reads (verified in [`test_a_channel_the_second_convolution_still_reads_is_kept`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/scripts/test_prune_channels.py#L60-L69)). At iteration 144 of `v5`, 136 of the 576 residual-block intermediate channels failed this threshold (440 kept, [`deploy-v5-pruned.yaml#L2`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L2)).

## Why Adam With L2 Weight Decay Shrinks Unused Weights to Zero

Before `v6b`, [`train.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/train.py#L56-L67) built `torch.optim.Adam(model.parameters(), lr=init_lr, weight_decay=cfg.training.weight_decay)`. In `v5` ([`v5-small-6x96.yaml#L45-L46`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96.yaml#L45-L46)) and the initial `v6` run, `weight_decay` was 0.0001, applied uniformly to every parameter tensor — including `Conv2d` biases and `BatchNorm2d` scale and shift parameters.

In PyTorch's `torch.optim.Adam`, `weight_decay` implements coupled L2 regularization by adding $\lambda \theta_t$ to the loss gradient $g_t = \nabla_\theta \mathcal{L}(\theta_t)$ *before* updating the exponential moving averages $m_t$ and $v_t$:

$$
\begin{aligned}
\tilde{g}_t &= g_t + \lambda \theta_t \\
m_t &= \beta_1 m_{t-1} + (1 - \beta_1)\tilde{g}_t, \quad v_t = \beta_2 v_{t-1} + (1 - \beta_2)\tilde{g}_t^2 \\
\hat{m}_t &= \frac{m_t}{1 - \beta_1^t}, \quad \hat{v}_t = \frac{v_t}{1 - \beta_2^t}, \quad \theta_{t+1} = \theta_t - \eta \frac{\hat{m}_t}{\sqrt{\hat{v}_t} + \epsilon}
\end{aligned}
$$

When a weight no longer receives signal from the training loss ($g_t \approx 0$), the combined gradient becomes $\tilde{g}_t \approx \lambda \theta_t$. Because Adam divides $\hat{m}_t$ by $\sqrt{\hat{v}_t} + \epsilon$, the factor $\lambda$ cancels out whenever $|\lambda \theta_t| \gg \epsilon$ (PyTorch default $\epsilon = 10^{-8}$):

$$
\frac{\hat{m}_t}{\sqrt{\hat{v}_t} + \epsilon} \approx \frac{\lambda \theta_t}{|\lambda \theta_t|} = \operatorname{sign}(\theta_t)
$$

Instead of shrinking proportionally by $\eta \lambda \theta_t$, an unused parameter steps toward zero at nearly the **full learning rate** $\eta$ per optimizer step, regardless of how small $\lambda$ is, until $|\lambda \theta_t|$ falls to the scale of $\epsilon$ or $\theta_t$ collapses around zero.

**AdamW** decouples weight decay from the adaptive gradient moments: $m_t$ and $v_t$ track only the unregularized gradient $g_t$, and decay is applied directly outside the adaptive ratio:

$$
\theta_{t+1} = \theta_t - \eta \left( \frac{\hat{m}_t}{\sqrt{\hat{v}_t} + \epsilon} + \lambda \theta_t \right) = \theta_t - \eta \frac{\hat{m}_t}{\sqrt{\hat{v}_t} + \epsilon} - \eta \lambda \theta_t
$$

When $g_t = 0$, $\hat{m}_t = 0$, so each step simply multiplies the weight by $(1 - \eta \lambda)$. With `lr = 0.001` and `weight_decay = 0.0001`, a single step changes $\theta_t$ by a factor of $1 - 10^{-7}$ rather than subtracting 0.001.

## Denormal Float32 Weights and the Intel CPU Slowdown

Once `Adam` with L2 decay drives unused parameters down past the `1e-38` scale, many of those weights do not hit exact 0.0 — they linger in the IEEE 754 `float32` **subnormal (denormal)** range.

### IEEE 754 Binary32 Subnormals

An IEEE 754 single-precision (`float32`) number uses 1 sign bit $s$, 8 exponent bits $E \in \{0, \dots, 255\}$ (bias 127), and 23 fraction bits $f = \sum_{i=1}^{23} b_{23-i} 2^{-i}$:

$$
x = \begin{cases}
(-1)^s \cdot 2^{E - 127} \cdot \left(1 + \sum_{i=1}^{23} b_{23-i} 2^{-i}\right) & \text{if } 1 \le E \le 254 \quad (\text{normal}), \\[8pt]
(-1)^s \cdot 2^{-126} \cdot \left(0 + \sum_{i=1}^{23} b_{23-i} 2^{-i}\right) & \text{if } E = 0,\; f \neq 0 \quad (\text{subnormal}), \\[6pt]
(-1)^s \cdot 0 & \text{if } E = 0,\; f = 0 \quad (\text{zero}).
\end{cases}
$$

The smallest positive normal `float32` value is $2^{-126} \approx 1.175 \times 10^{-38}$. Below $2^{-126}$, `E` reaches 0, the implicit leading 1 disappears (`0.f`), and positive subnormal values span $[2^{-149}, 2^{-126}) \approx [1.401 \times 10^{-45}, 1.175 \times 10^{-38})$.

### Why Intel Workers Slowed Down ~20x and How Evaluation Games Flush Them

Hardware floating-point units optimize for normalized `1.f` significands. When an x86 processor without flush-to-zero (FTZ) or denormals-are-zero (DAZ) enabled encounters subnormal operands or results during multiply-accumulate loops, Intel microarchitectures commonly trap to a microcode assist, adding tens to hundreds of cycles per operation.

During `v5` training on the 100-vCPU Ray cluster ([`cluster_v5.yaml#L1-L6`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/infra/training/cluster/cluster_v5.yaml#L1-L6)), self-play used `bfloat16` (`local_dtype: bfloat16`), whereas the round-robin evaluation ladder and reference matches ran single-threaded CPU `float32` inference. Because GCP's `europe-west2` quota mixed 9 AMD `c4d-standard-8` nodes (72 vCPUs) with 2 Intel C4 nodes (`c4-standard-8` and `c4-standard-4`, 12 vCPUs), the Intel workers stalled on `v5`'s `~281,000` denormal weights ([`v5-small-6x96-cont9.yaml#L3-L10`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L3-L10)):

| Execution path | Node CPU | `float32` flush denormals | Latency per position | Source |
| --- | --- | --- | --- | --- |
| CPU `float32` (eval) | Intel C4 (`c4-standard-*`) | Off (default) | `206–258 ms` | [`v5-small-6x96-cont9.yaml#L7`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L7) |
| CPU `float32` (eval) | Intel C4 (`c4-standard-*`) | `torch.set_flush_denormal(True)` | 10 ms | [`v5-small-6x96-cont9.yaml#L8`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L8) |

| CPU `bfloat16` (self-play) | Intel C4 & AMD C4D | — | 5 ms | [`v5-small-6x96-cont9.yaml#L8-L9`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L8-L9) |

Those `206–258 ms` evaluations on the two Intel nodes stretched the in-run ladders at iterations 135 (120 games, 4 random opening plies) and 140 (240 games, 3 random opening plies) to 48 to 62 minutes while holding the entire 100-vCPU cluster (`v5-small-6x96-cont8.yaml#L10`, `v5-small-6x96-cont9.yaml#L5-L6`). See [Measuring Strength When the First Player Wins](/docs/optimization/evaluation) and [Running the Training Cluster](/docs/optimization/training-infrastructure) for the evaluation design and cluster layout.

Commit [`719fe38`](https://github.com/sungyongcho/gomoku/commit/719fe38) added `torch.set_flush_denormal(True)` inside both CPU `float32` evaluation worker functions: [`play_ladder_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/ladder.py#L75-L77) and [`play_game`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/eval/reference_match.py#L90-L92):

```python
# alphazero/gomoku/alphazero/eval/ladder.py:75-77
torch.set_num_threads(1)
# Weights decayed to denormals make float32 inference about 20 times slower on Intel CPUs.
torch.set_flush_denormal(True)
```

Enabling FTZ/DAZ cut Intel `float32` inference latency from `206–258 ms` down to 10 ms per position (`~20x` speedup). In addition, [`v5-small-6x96-cont9.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96-cont9.yaml#L9-L10) dropped the mid-run ladder for iterations `141–150` and deferred final checkpoint selection to the standalone `scripts/ladder.py` run after training.

## Keeping Channels Alive With `AdamW`

To prevent future training runs from killing filters in the first place, commit [`719fe38`](https://github.com/sungyongcho/gomoku/commit/719fe38) added `optimizer: Literal["adam", "adamw"] = "adam"` to [`TrainingConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L104-L106) and extracted optimizer creation into [`build_optimizer`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/alphazero/learning/optimizer.py#L10-L36), called by both [`train.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/train.py#L66) and [`pretrain.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/pretrain.py#L179):

```python
# alphazero/gomoku/alphazero/learning/optimizer.py:24-36
if training.optimizer == "adam":
    return torch.optim.Adam(
        model.parameters(), lr=learning_rate, weight_decay=training.weight_decay
    )
decayed = [p for p in model.parameters() if p.requires_grad and p.ndim > 1]
plain = [p for p in model.parameters() if p.requires_grad and p.ndim <= 1]
return torch.optim.AdamW(
    [
        {"params": decayed, "weight_decay": training.weight_decay},
        {"params": plain, "weight_decay": 0.0},
    ],
    lr=learning_rate,
)
```

Two details define this setup:

- **Default `"adam"` preserved**: Existing configurations without an `optimizer` field keep `torch.optim.Adam` so earlier configs remain reproducible.
- **1D parameters excluded from decay**: When `optimizer: adamw` is set, only multi-dimensional tensors (`p.ndim > 1`: `Conv2d` 4D kernels and `Linear` 2D weight matrices) receive `weight_decay`. All 1D parameters (`p.ndim <= 1`: `BatchNorm2d` scale $\gamma$ and shift $\beta$, plus `Conv2d` and `Linear` biases) get `weight_decay = 0.0`, so decay cannot directly collapse normalization scales toward zero.

The unit test [`test_a_channel_without_gradient_survives_adamw_and_vanishes_under_adam`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/alphazero/learning/optimizer_test.py#L53-L69) verifies this behavior on a `Conv2d(1, 2, 3) -> BatchNorm2d(2)` module over 300 zero-gradient steps (`lr = 0.01`, `weight_decay = 0.1`): `Adam` pushes both `conv.weight.abs().max()` and `bn.weight.abs().min()` below `1e-3`, whereas `AdamW` leaves `conv.weight.abs().max() > 0.1` and `bn.weight.abs().min() == 1.0`.

In practice, [`v6b-10x128.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v6b-10x128.yaml#L7-L10) restarted the `10x128` network with `optimizer: adamw` and `weight_decay: 0.01`. Pretrained on the same `v5` replay shards (iterations `96–143`, four passes, held-out iteration 144), `v6b` kept every one of its 2,691 convolution filters alive (against 497 dead filters and 36% zero weights under `Adam`) and lowered held-out loss from `policy 2.054, value 0.319` to `policy 2.043, value 0.316` (see [A Bigger Network and Why It Was Not Deployed](/docs/optimization/bigger-network)).

## Pruning Dead Channels After Training

Switching to `AdamW` protects new runs, but the deployed `v5` iteration 144 checkpoint had already been trained with `Adam` and still carried 136 dead channels across its 6 residual blocks (576 block channels total). Even with zero weights, a 96-channel convolution still executes multiplications and additions for those dead channels on CPU.

### Why Intermediate Channels Can Be Removed Without Changing Outputs

In `ResBlock`, the block's input and output tensors must keep `num_hidden = 96` channels because the skip connection `x += residual` adds the input directly to `bn2(conv2(...))`. Between `conv1` and `conv2`, however, the `mid_channels` intermediate feature maps exist only inside the block:

$$
\text{ResBlock}(x) = \operatorname{ReLU}\!\Big(\operatorname{BN}_2\big(\operatorname{Conv}_2\big(\operatorname{ReLU}(\operatorname{BN}_1(\operatorname{Conv}_1(x)))\big)\big) + x\Big)
$$

If intermediate channel $c$ has zero incoming weights in `conv2.weight[:, c, :, :]`, its activation map contributes $0$ to every output channel of `conv2`, regardless of `conv1` or `bn1` for channel $c$. Removing channel $c$ therefore requires deleting index $c$ from:

1. `conv1.weight` along its output-channel axis (`dim=0`),
2. `conv1.bias`,
3. `bn1.weight`, `bn1.bias`, `bn1.running_mean`, and `bn1.running_var`, and
4. `conv2.weight` along its input-channel axis (`dim=1`).

`conv2.bias` and all of `bn2` belong to the block's `num_hidden` output channels and stay untouched.

### Implementation and Output-Equality Check

Commit [`79efde7`](https://github.com/sungyongcho/gomoku/commit/79efde7) added `resblock_mid_channels: list[int] | None = None` to [`ModelConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L49-L60) (validated to contain one positive width per residual block), wired it into [`PolicyValueNet`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/model/policy_value_net.py#L117-L120), and implemented [`prune_state_dict`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/prune_channels.py#L30-L52):

```python
# alphazero/gomoku/scripts/prune_channels.py:40-52
while f"res_blocks.{block}.conv2.weight" in state:
    prefix = f"res_blocks.{block}."
    used = state[prefix + "conv2.weight"].abs().amax(dim=(0, 2, 3)) >= threshold
    if not bool(used.any()):
        used[0] = True  # a block needs at least one channel
    pruned[prefix + "conv1.weight"] = state[prefix + "conv1.weight"][used].clone()
    pruned[prefix + "conv1.bias"] = state[prefix + "conv1.bias"][used].clone()
    for name in ("weight", "bias", "running_mean", "running_var"):
        pruned[prefix + "bn1." + name] = state[prefix + "bn1." + name][used].clone()
    pruned[prefix + "conv2.weight"] = state[prefix + "conv2.weight"][:, used].clone()
    widths.append(int(used.sum()))
    block += 1
```

### Measured Results on `v5` Iteration 144

Running `prune_channels.py` on `v5` iteration 144 produced [`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L1-L26) with the following measurements:

- **Block widths kept**: `resblock_mid_channels: [81, 77, 84, 74, 65, 59]`, keeping 440 of 576 residual-block channels (76.4%, 136 removed).
- **Compute reduction**: The narrowed residual blocks perform 76% of the unpruned blocks' multiply-adds ([`deploy-v5-pruned.yaml#L3-L4`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L3-L4)).
- **Output agreement**: Policy logits and value outputs stayed the same to within `5e-6` over the script's 200 sampled positions ([`deploy-v5-pruned.yaml#L3`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L3); no separate per-head breakdown was recorded). No standalone playing-strength match was run between the pruned and unpruned checkpoints.
- **Serving speed on Arm**: On the Oracle Cloud `VM.Standard.A1.Flex` instance (2 Arm Neoverse-N1 cores, static `int8` ONNX Runtime, 2 threads, 2.5-second time limit via [`03_bench_search.sh`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/03_bench_search.sh) over 12 positions), `v5` iteration 144 increased from 613 searches per move as trained to 671 searches per move with dead channels removed (+9.5%, [`deploy/alphazero-oracle/README.md#L21-L24`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L21-L24)). See [Serving on a 2-Core Arm Instance](/docs/optimization/free-arm-hosting) for the full deployment and [Answering by the Clock](/docs/optimization/time-limited-serving) for the static `int8` quantization path.
