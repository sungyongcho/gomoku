# Answering by the Clock

Until November 2026, the AlphaZero server ran a fixed `num_searches: 200` simulations per move regardless of the host CPU (see [V4 `deploy.yaml`](https://github.com/sungyongcho/gomoku/blob/33397d3/alphazero/configs/deploy.yaml#L19-L28)). Moving off a paid 4-vCPU GCP machine onto an Always Free 2-core Arm instance required bounding answer latency independently of processor speed while fitting as many quality-weighted simulations as possible inside the 3-second move target (see [Why This Section Exists](/docs/optimization/intro)).

Commit [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac) redesigned the serving path around a time budget: stopping native C++ MCTS at a 2.5-second clock limit, scoring unvisited moves from the parent node's value, breaking equal-visit ties with the network's policy prior, forwarding recent-move history in WebSocket requests, and replacing the dynamic `onnx-int8` backend of the example deployment settings with calibrated static `int8` inference. Commit [`cc3eb70`](https://github.com/sungyongcho/gomoku/commit/cc3eb70) followed with an `fpu_reduction` option after measuring flat visit distributions at 0.0.

## Stopping Search at a Time Limit

In the V4 deployment, answer latency was directly tied to hardware throughput:

$$
T_{\text{move}} \approx N_{\text{searches}} \cdot (t_{\text{tree}} + t_{\text{infer}})
$$

With a fixed `num_searches: 200`, the 12x128 network took roughly 2.5 seconds on a GCP `c2d-standard-4` VM, whereas on two Arm Neoverse-N1 cores even the smaller 6x96 network completes only 196 searches in 2.5 seconds as float32 ONNX. Fixing the simulation count meant slower hardware or larger networks missed the 3-second target.

### How the Clock Check Works

Commit [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac) added `time_limit_s: float | None = None` to [`MctsConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L138-L139). When serving calls [`CppSearchStrategy._run_encoded_mcts`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/sequential/cpp_strategy.py#L196-L203), it passes `time_limit_s` through [`gomoku_cpp.MctsEngine.run_mcts_encoded`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/gomoku_bindings.cpp#L170-L181) into the native C++ search loop ([`MctsEngine::ContinueSimulationEncoded`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L291-L305)):

```cpp
// alphazero/cpp/src/MctsEngine.cpp:291-305
last_simulations_ = 0;
const auto started = std::chrono::steady_clock::now();
for (int i = 0; i < num_simulations; ++i) {
    if (stoppable && stop_requested_.load(std::memory_order_relaxed)) {
        break;
    }
    if (max_nodes > 0 && node_count_ >= max_nodes) {
        break;
    }
    if (time_limit_s > 0.0f && (i > 0 || root_->is_expanded)) {
        const std::chrono::duration<float> elapsed = std::chrono::steady_clock::now() - started;
        if (elapsed.count() >= time_limit_s) {
            break;
        }
    }
```

Two details in that check govern real response times:

- **Guaranteed first expansion**: The guard `(i > 0 || root_->is_expanded)` skips the clock check on iteration 0 when the root has not yet been expanded, ensuring at least one simulation runs so there are root children and priors to pick from even under extreme CPU contention.
- **Per-iteration check and the 0.5-second margin**: Elapsed time against `std::chrono::steady_clock` is tested *before* each simulation starts, not mid-inference. Once a simulation enters leaf evaluation, it runs to completion and backs up before the loop exits. Serving configs therefore set `time_limit_s: 2.5`, leaving a 0.5-second margin inside the 3-second move target for the in-flight final evaluation, state reconstruction, and WebSocket serialization. On the Oracle A1 host without tree reuse, full-game measurements with `time_limit_s: 2.5` averaged 2.52 s per answer with a 2.59 s maximum ([`deploy/alphazero-oracle/README.md`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L121-L127)). When tree reuse is enabled, [`SearchSession.best_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L173-L176) also subtracts any time already spent stopping a background ponder search from `time_limit_s` before entering the loop (see [Using the Opponent's Time](/docs/optimization/tree-reuse-and-pondering)).

### What Happens to `num_searches`

The loop still bounds iterations by `num_simulations`, so in serving configurations — [`deploy.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy.yaml#L20-L23), [`deploy-v5.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5.yaml#L19-L23), [`deploy-v5-pruned.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L24-L26), and [`deploy-v6b.yaml`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v6b.yaml#L21-L25) — `num_searches` is set to 100000. That cap is high enough that the clock always ends the search first on CPU (unless the root itself is terminal, in which case the loop breaks after one check). Meanwhile, `time_limit_s` defaults to `None` (`0.0f` in C++), so training self-play and fixed-count arena evaluation still run exact simulation counts.

Because the clock stops the loop regardless of CPU speed or network dimensions, latency becomes hardware-independent up to one leaf forward pass. Instead of slowing down the user interface, slower hardware or a larger network simply reduces $N_{\text{new}} \approx T_{\text{budget}} \cdot r_{\text{search}}$.

## First-Play Urgency (FPU)

In standard MCTS, an unvisited child has `visit_count == 0`, so it has no empirical mean value $Q(s, a)$ yet. Previously, both the Python path ([`TreeNode.get_ucb`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/treenode.py#L95-L128)) and the native C++ path defaulted unvisited children to $Q = 0.0$.

On a 19×19 board with up to 361 legal moves, assuming $Q = 0.0$ for untried moves distorts selection whenever the current position is far from equal:

- When the parent position is **losing** ($V_{\text{parent}} < 0$, say $-0.7$), every visited defense backs up a negative value around $-0.7$, whereas every unvisited move still looks like $0.0$. That +0.7 bias pulls visits onto dozens of unvisited moves across the board instead of deepening the best defense.
- When the parent position is **winning** ($V_{\text{parent}} > 0$), untried alternatives start at $0.0$, which penalizes them relative to the parent's positive mean.

### Parent-Value FPU and Sign Convention in `MctsEngine`

As shown in [Monte Carlo Tree Search with PUCT](/docs/alphazero/mcts), [`MctsEngine::Backup`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L793-L805) accumulates `value_sum` from each node's own `player_to_play` perspective, flipping the sign at every parent step up the path. Inside [`MctsEngine::CalculateUcb`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L807-L828), the C++ selection formula is:

$$
\text{UCB}(s, a) = Q(s, a) + c_{\text{puct}} \cdot P(s, a) \cdot \frac{\sqrt{N_{\text{parent}} + L_{\text{parent}} + 1}}{1 + N_{\text{child}} + L_{\text{child}}}
$$

where $N_{\text{parent}}$ (`parent->visit_count`) and $N_{\text{child}}$ (`child->visit_count`) are completed visits, and $L_{\text{parent}}, L_{\text{child}}$ (`virtual_loss`) are in-flight virtual losses (0 during sequential serving with `batch_infer_size: 1`). Notice the `+ 1` inside the square root, matching the C++ implementation rather than $\sqrt{\max(1, N(s))}$ in the Python path.

Because `child` is the opponent's turn to play, a visited child's value is negated into the parent's perspective. By contrast, `parent->value_sum / parent->visit_count` is **already** in the parent's perspective, so the FPU branch takes it without a minus sign and subtracts `fpu_reduction_`:

$$
Q(s, a) = \begin{cases}
-\dfrac{W_{\text{child}} + L_{\text{child}}}{N_{\text{child}} + L_{\text{child}}} & \text{if } N_{\text{child}} > 0, \\[8pt]
\dfrac{W_{\text{parent}}}{N_{\text{parent}}} - r_{\text{fpu}} & \text{if } N_{\text{child}} = 0 \text{ and } \texttt{fpu\_from\_parent} \text{ and } N_{\text{parent}} > 0, \\[6pt]
0 & \text{otherwise.}
\end{cases}
$$

Here $W_{\text{child}}$ is `child->value_sum`, $W_{\text{parent}}$ is `parent->value_sum`, and $r_{\text{fpu}}$ is `fpu_reduction_`:

```cpp
// alphazero/cpp/src/MctsEngine.cpp:816-827
float q = 0.0f;
if (child_visit_count > 0) {
    // Pending evaluations count as losses so batched selection spreads out.
    q = -(child->value_sum + static_cast<float>(child_virtual_loss))
        / static_cast<float>(child_visits);
} else if (fpu_from_parent_ && parent->visit_count > 0) {
    q = parent->value_sum / static_cast<float>(parent->visit_count) - fpu_reduction_;
}
const float u = c_puct_ * prior
    * std::sqrt(static_cast<float>(parent_visits + 1))
    / (1.0f + static_cast<float>(child_visits));
return q + u;
```

In [`SequentialEngine`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/sequential/engine.py#L39-L44), `fpu_from_parent` and `fpu_reduction` are forwarded from [`MctsConfig`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/utils/config/loader.py#L151-L154) into the native C++ `MctsEngine` only; the pure-Python `TreeNode.get_ucb` remains unchanged.

### Why `fpu_reduction = 0` Left Search Targets Flat

Commit [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac) initially enabled `fpu_from_parent: true` with no reduction ($r_{\text{fpu}} = 0$). Measuring search behavior on 2026-11-07 showed that setting $r_{\text{fpu}} = 0$ left root visit distributions near uniform ([`cc3eb70`](https://github.com/sungyongcho/gomoku/commit/cc3eb70), [`v5-small-6x96.yaml#L28`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96.yaml#L28)).

The mechanism follows directly from the UCB formula. Suppose a visited move $a_1$ returns a backed-up value near the parent's mean, so $Q(s, a_1) \approx W_{\text{parent}} / N_{\text{parent}}$. After that single visit, its exploration denominator $1 + N(s, a_1)$ doubles from $1$ to $2$, halving its exploration term $U$. Meanwhile, every unvisited move $a_2$ receives $Q_{\text{FPU}} = W_{\text{parent}} / N_{\text{parent}} - 0 = Q(s, a_1)$ with denominator $1$. Unless $P(s, a_1) > 2 P(s, a_2)$, $a_2$ immediately outscores $a_1$, causing search to spread one visit per move across the board instead of revisiting tried moves (verified in [`selfplay_targets_test.py#L207-L223`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/alphazero/selfplay_targets_test.py#L207-L223), where a flat evaluator yields `max(visits) == 1` at `fpu_reduction = 0.0`).

Subtracting `fpu_reduction` forces an unvisited move's prior bonus to overcome a penalty before taking visits away from moves already evaluated near $W_{\text{parent}} / N_{\text{parent}}$. On 2026-11-07, 0.0 left targets near uniform while `0.2+` narrowed the search to about 8 moves, so v5 training ([`v5-small-6x96.yaml#L27-L28`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/v5-small-6x96.yaml#L27-L28)) and serving ([`deploy-v5.yaml#L22-L23`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5.yaml#L22-L23), [`deploy-v5-pruned.yaml#L36-L37`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/configs/deploy-v5-pruned.yaml#L36-L37)) used `fpu_from_parent: true` with `fpu_reduction: 0.1`. No standalone head-to-head match was run to measure a win-rate delta for FPU alone.

## Prior Tie-Breaks at Move Selection

At serving time (`temperature = 0`), the engine selects the move with the most root visits. Before [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac), [`CppSearchStrategy._sync_visits`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/sequential/cpp_strategy.py#L217-L236) populated `child.prior` with `count / total_visits`, [`SearchEngine.get_search_result`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/pvmcts/search/engine.py#L309-L348) returned a normalized visit array, and `AlphaZeroEngine.get_best_move` returned `int(np.argmax(policy))`.

When two or more moves finish with equal visit counts, `np.argmax` breaks ties by the lowest flat board index `x + y * 19` — picking whichever tied move sits closer to `(0, 0)` (the top-left corner). Worse, when `root.visit_count == 1`, `get_search_result` fell back to a uniform mask over all legal moves, so `np.argmax` picked the first legal square on the board regardless of the policy network. Under a 2.5-second time limit, where fewer simulations complete than in deep offline search, visit ties (such as 1 visit each across several candidates) happen more readily, and throwing away the policy head's ordering at a tie sacrifices signal already computed during root expansion.

Commit [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac) added [`MctsEngine::RootPriors`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/MctsEngine.cpp#L242-L253) to return `(move_idx, prior)` from the root's legal-masked softmax priors, passed those priors into `_sync_visits`, and replaced `np.argmax(policy)` with [`AlphaZeroEngine._most_visited_action`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/engine.py#L177-L188):

```python
# alphazero/server/engine.py:177-188
def _most_visited_action(self, root: TreeNode, policy: np.ndarray) -> int:
    """Pick the most visited move, breaking visit ties by the network prior."""
    if not root.children:
        return int(np.argmax(policy))
    x, y = max(
        root.children,
        key=lambda action: (
            root.children[action].visit_count,
            root.children[action].prior,
        ),
    )
    return int(x + y * self.game.col_count)
```

When tree reuse is enabled, [`SearchSession.best_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/session.py#L182-L185) uses the same `(visits, priors[move_idx])` key (verified in [`test_move_selection.py`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/tests/server/test_move_selection.py#L24-L31)). Any separate playing-strength gain from prior tie-breaking alone was not measured.

## Recent-Move History in the Network Input

As described in [The Policy-Value Network](/docs/alphazero/neural-network), with `history_length: 5` the network takes a `13x19x19` tensor where planes 8 through 12 are one-hot encodings of the last 5 moves, ordered newest first (`history[0]` in plane 8, `history[4]` in plane 12). In C++ self-play and tree traversal, [`GomokuCore::apply_move`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/GomokuCore.cpp#L217-L225) prepends each move to `state.history` up to `history_length_`, and [`GomokuCore::write_state_features`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/cpp/src/GomokuCore.cpp#L404-L416) writes all 5 entries into channels `8–12`.

Before [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac), WebSocket requests from the frontend included only `lastPlay` (a single move), so [`frontend_to_gamestate`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/protocol.py#L129-L174) set `history = (last_move_idx,)`. At the search root, plane 8 had the last move, but planes 9 through 12 were always all zeros — creating a train–serve mismatch on 4 of the 13 input channels and hiding which stones on the board were played in the preceding 2 to 5 plies.

Commit [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac) added an optional `recentMoves?: { x: number; y: number }[]` field to [`SocketMoveRequest`](https://github.com/sungyongcho/gomoku/blob/f416558/front/types/game.ts#L50), populated from the last 5 moves (`histories.value.slice(-5)` in oldest-first order) across [`game.vue`](https://github.com/sungyongcho/gomoku/blob/f416558/front/pages/game.vue#L185-L187), [`debug.vue`](https://github.com/sungyongcho/gomoku/blob/f416558/front/pages/debug.vue#L129-L131), and [`TestPageClient.vue`](https://github.com/sungyongcho/gomoku/blob/f416558/front/components/TestPageClient.vue#L105). On the server, [`_extract_history`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/protocol.py#L110-L126) reverses the list so `GameState.history` is newest first, verifies that `recentMoves` ends with `lastPlay`, and falls back to `(last_move_idx,)` when `recentMoves` is omitted so older clients still work. No standalone strength test was run for history reconstruction in isolation.

## Static Int8 Quantization of the ONNX Model

Because `time_limit_s: 2.5` caps wall-clock search time and `batch_infer_size: 1` runs one board at a time during serving, CPU throughput $r_{\text{search}}$ depends almost entirely on single-sample neural-network latency $t_{\text{infer}}$.

### Affine Quantization and Static Calibration vs. Dynamic Quantization

Uniform affine quantization maps an 8-bit integer $q$ back to an approximate floating-point value $x$ using a scale $s > 0$ and integer zero-point $z$:

$$
x \approx s \cdot (q - z), \qquad q = \operatorname{clip}\!\left(\operatorname{round}\!\left(\frac{x}{s}\right) + z,\; q_{\min},\; q_{\max}\right)
$$

Before this change the repository's example settings chose `ALPHAZERO_INFER_BACKEND=onnx-int8` (which backend the live V4 server used is not recorded; unset, it is PyTorch float32). That backend ran [`_quantize_dynamic`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/inference/onnx_inference.py#L43-L52) via `onnxruntime.quantization.quantize_dynamic`. Dynamic quantization converts weights offline, but because activation ranges are unknown ahead of time, ONNX Runtime inserts `DynamicQuantizeLinear` nodes that scan each activation tensor at runtime to compute $s$ and $z$ before running integer convolutions or matrix multiplies (`ConvInteger`, `MatMulInteger`), while leaving operations such as residual `Add` and `Flatten` in float32. Computing those min/max statistics on every layer adds overhead on every single leaf evaluation.

Static quantization (`ALPHAZERO_INFER_BACKEND=onnx-static`, set in [`.env.example`](https://github.com/sungyongcho/gomoku/blob/f416558/.env.example#L43) and [`deploy/alphazero-oracle/docker-compose.yml`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/docker-compose.yml#L18-L21)) instead determines activation scales and zero-points once at server startup using representative calibration boards, removing runtime range calculation.

### Calibration Data and Quantized Operators

When `ALPHAZERO_INFER_BACKEND=onnx-static`, [`AlphaZeroEngine._calibration_positions`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/server/engine.py#L126-L147) generates 100 calibration inputs (with a fixed `seed = 7`) by playing games with the float32 PyTorch model rather than feeding synthetic noise:

1. Start from an empty board and step through a random game length of 4 to 60 plies (stopping early if terminal).
2. At each ply, encode the state as `float32`, evaluate policy logits with `self.model`, mask occupied squares to $-\infty$, and sample uniformly from the top 3 legal moves.
3. Collect encoded positions across games until at least 100 exist, shuffle them, and take the first 100.

[`_export_to_onnx`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/inference/onnx_inference.py#L13-L40) exports the PyTorch model (`opset_version=17`, `dynamo=False`, `do_constant_folding=True`, folding `BatchNorm2d` into `Conv`). [`_quantize_static`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/inference/onnx_inference.py#L65-L88) runs `quant_pre_process(..., skip_symbolic_shape=True)`, then feeds the 100 calibration samples one by one (`batch_size = 1`) through [`_CalibrationReader`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/inference/onnx_inference.py#L55-L62) into `quantize_static`:

- `quant_format=QuantFormat.QDQ` — inserts `QuantizeLinear` / `DequantizeLinear` pairs around operators.
- `activation_type=QuantType.QUInt8` ($[0, 255]$) and `weight_type=QuantType.QInt8` ($[-128, 127]$) with `per_channel=True` (separate scale and zero-point per output channel).
- `op_types_to_quantize=None`, so ONNX Runtime quantizes every operator type its QDQ quantizer supports by default. After constant folding merges batch normalization into the convolutions, most of the graph's work is in the `Conv` layers of the residual tower, which become integer operations. Which individual nodes stay in float32 was not recorded.

Commit [`a72a3ac`](https://github.com/sungyongcho/gomoku/commit/a72a3ac) also wired `ALPHAZERO_INFER_THREADS` into ONNX Runtime's `SessionOptions` (`intra_op_num_threads = num_threads`, and `inter_op_num_threads = 1 if num_threads else 0`).

### Measured Search Budget on Two Neoverse-N1 Cores

Running [`gomoku.scripts.bench_search`](https://github.com/sungyongcho/gomoku/blob/f416558/alphazero/gomoku/scripts/bench_search.py) over a 2.5-second budget on two Neoverse-N1 cores of the Oracle Cloud `VM.Standard.A1.Flex` instance produced the following search counts ([`deploy/alphazero-oracle/README.md`](https://github.com/sungyongcho/gomoku/blob/f416558/deploy/alphazero-oracle/README.md#L11-L24)):

| Network | Backend | Threads | Searches in 2.5 s |
| --- | --- | --- | --- |
| 6x96 (v5) | static int8 ONNX | 2 | 634 |
| 10x128 (v6b) | static int8 ONNX | 2 | 272 |
| 6x96 (v5) | static int8 ONNX | 1 | 392 |
| 6x96 (v5) | float32 ONNX | 2 | 196 |

Dynamic `int8` was not benchmarked in that table on Neoverse-N1, and no quantized-versus-float32 policy-agreement or playing-strength comparison was recorded for the deployed checkpoints.

For the search budget $N_{\text{new}} \approx T_{\text{budget}} \cdot r_{\text{search}}$, the measurements establish three things directly:

- Switching the 6x96 model on 2 threads from `float32 ONNX` to `static int8 ONNX` raises the 2.5-second search count from 196 to 634 (3.23x), turning a sub-200-search budget into more than 600 searches inside the same 3-second move target.
- Using both cores (2 threads vs 1 thread) increases `static int8` searches from 392 to 634 (1.62x).
- Under `static int8` on 2 threads, `6x96` completes 634 searches where `10x128` completes 272 (2.33x as many simulations in the same clock window). Whether the smaller network's higher search budget outweighs the larger network's per-position accuracy at equal thinking time is examined in [A Bigger Network and Why It Was Not Deployed](/docs/optimization/bigger-network). Later on the same host, cutting dead channels out of v5 iteration 144 raised the on-instance `03_bench_search.sh` count from 613 to 671 (see [What Adam With Weight Decay Did to the Network](/docs/optimization/dead-channels) and [Serving on a 2-Core Arm Instance](/docs/optimization/free-arm-hosting)).
